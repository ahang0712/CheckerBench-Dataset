# CWE-770: Allocation Without Limits or Throttling
> Tier: 2 | Global samples: 26

## 1. Typical Code Patterns

CWE-770 covers resource exhaustion via unbounded allocation in C/C++. The dominant patterns are:

- **Loop-based unbounded accumulation**: Reallocating or appending inside a `while`/`for` loop whose termination does not depend on a fixed bound (e.g., reading from a network socket until a sentinel byte, calling `realloc()` or `std::vector::push_back()` per iteration without a cap).
- **Untrusted size in allocation call**: Passing a value derived directly from external input (network, file, environment) to `malloc(n)`, `calloc(n, ...)`, `new T[n]`, or `kmalloc(n)` without validation against a maximum.
- **Unbounded string operations**: Using `strcat`, `sprintf`, `vsnprintf` (with unknown size), or repeated `getline`/`fread` into a resizable buffer without limiting total bytes consumed.
- **Recursive allocation**: Functions that call `malloc`/`new` on each recursive frame with depth controlled only by untrusted input (e.g., parsing nested JSON/XML into heap nodes).
- **Implicit container growth**: `std::string::operator+=` / `std::vector::push_back` in a loop reading external data without `reserve()` or size caps.

The common root: *the total allocated bytes is bounded only by attacker-controlled data, not by a programmatic limit.*

## 2. CSA Checker Architecture Recommendations

- **Base class**: `BuiltinBugCheck` or a custom `Checker` (not `malloc::MallocChecker` — that focuses on leaks/use-after-free, not allocation limits). A dedicated `AllocationSizeChecker` is preferred.
- **Callbacks**: `checkPostCall` (for allocation functions: `malloc`, `calloc`, `realloc`, `operator new`, `kmalloc`), `checkEndAnalysis` (to summarize per-path total), and `checkBranchCondition` (to detect loop bounds).
- **Tracking granularity**: Symbolic region for each allocation site. Track both *per-allocation size* and *cumulative allocated bytes* along a path. Flag when cumulative bytes exceed a heuristic threshold (e.g., >64 MB) or when size expression is tainted without an intervening cap check.
- **Cross-reference**: See `csa_checker_patterns.md` §"Resource Exhaustion Checkers" for loop-bound inference and taint-propagation wiring.
- **State partitioning**: Use a `ProgramState` trait `AllocationMap` mapping `SymbolRef → (SizeExpr, CallSite)`. Register a `checkDeadSymbols` to prune freed regions.

## 3. Known High-Frequency False Positive Patterns

- **Bounded by protocol or external contract**: The analyzer sees no upper bound, but the data source (e.g., a kernel netlink socket, an IPC channel) guarantees a max size. Suppress via configuration or allow-list of trusted source APIs.
- **One-shot fixed-size allocation**: `malloc(sizeof(T))` where the size is a constant — trivially safe; the checker must exclude constant sizes below a sane threshold (e.g., <1 MB).
- **Geometric growth with implicit cap**: `std::vector` doubling strategy stops at `max_size()`. Modeling this precisely avoids FP; if the analyzer cannot prove the cap, it should require explicit `reserve()` calls.
- **Test/debug code**: Allocations in `assert()` bodies or behind `#ifdef DEBUG` that are never reachable in production builds.

## 4. Generic Discriminant Features

| Textbook (likely true positive) | Variant (likely FP / low-severity) |
|---|---|
| Allocation size = tainted integer without `min(MAX, val)` check | Allocation size = constant or derived from a constant bound |
| Loop runs while `ptr = read()` continues (no iteration cap) | Loop has a fixed trip count known at compile time |
| Total allocated bytes grows monotonically with input | Allocation is freed before next allocation (no accumulation) |
| `realloc()` or `append()` in a loop without size ceiling | Single allocation in a bounded error path |
| Container grows element-by-element from untrusted source | Container uses `reserve(N)` with N derived from a pre-scan |
