# CWE-399: Resource Management Errors
> Tier: 2 | Global samples: 35

## 1. Typical Code Patterns

CWE-399 is a **Category** grouping weaknesses where system resources (memory, file descriptors, sockets, locks, reference counts) are improperly acquired, used, or released. In C/C++ codebases the most tractable manifestations are:

- **Missing release of resource (CWE-772):** A resource (heap allocation via `malloc`/`new`, file via `open`/`fopen`, socket via `socket`, mutex via `pthread_mutex_lock`) is acquired but one or more control-flow paths omit the corresponding release (`free`/`delete`, `close`/`fclose`, `pthread_mutex_unlock`). This is the single most common pattern — typically an early-return or error path that skips cleanup.

- **Multiple releases of same resource (CWE-415 / CWE-1341):** `free(p)` called twice, or `close(fd)` called on an already-closed descriptor. The second release corrupts allocator metadata or recycles an fd that another thread just opened. Manifests in confusing cleanup logic where two different code paths both attempt to release the same handle.

- **Premature release / use of expired resource (CWE-826 / CWE-416 / CWE-910):** A resource is freed or closed while a reference to it remains live (dangling pointer, stale file descriptor). The subsequent use operates on freed memory or a recycled descriptor. Common when a resource is released inside a callback or signal handler but the outer scope still holds the handle.

- **Improper reference counting (CWE-911):** `AddRef`/`Release` or `refcount_inc`/`refcount_dec` calls are mismatched — either an extra decrement (premature destruction) or a missing decrement (leak). Typical in COM-style C++ and kernel kref/refcount patterns.

- **Resource acquisition without limits (CWE-770):** Allocation inside a data-dependent loop without a cap on total consumption, leading to resource exhaustion (memory, fd table, thread pool).

- **Missing initialization of resource (CWE-908 / CWE-909):** A handle variable is declared but not initialized before first use (e.g., `FILE *f;` then `fread(buf, 1, n, f);` without `fopen` — UB; or a mutex not initialized via `pthread_mutex_init`).

These patterns frequently overlap (a double-free often implies a missing nullification after the first free; a leak often coexists with premature release in different paths of the same function).

## 2. CSA Checker Architecture Recommendations

- **Base class**: `BuiltinBugChecker` with `Checker<check::PreCall, check::PostCall, check::DeadSymbols, check::EndFunction>`. For concurrency resources (lock/unlock), add `check::BranchCondition` to model lock-gate semantics.

- **Callbacks**:
  - `check::PreCall` / `check::PostCall` — intercept acquire/release API pairs. Maintain a `ProgramState` map (`SymbolRef → ResourceState{Acquired, Released, Escaped}`). Model paired APIs (`malloc`/`free`, `fopen`/`fclose`, `lock`/`unlock`, `Ref`/`Unref`) through a generic resource-registration table so adding new resource types does not require new checker classes.
  - `check::DeadSymbols` — detect resources that become unreachable without being released (leak detection).
  - `check::EndFunction` — detect resources still acquired at function exit (unless ownership is returned or transferred via a known output parameter).
  - `check::PostCall` (for `realloc`/`close`/`free`) — bifurcate state on success vs. failure to catch double-free and use-after-free.

- **Tracking granularity**: Key the resource state on `SymbolRef` (for heap memory) or a `ResourceHandle` abstraction wrapping file descriptors, socket IDs, lock counts. Use a `ProgramState::set<Trait>` with three-state model: `Acquired → Released → Invalid`. A transition from `Released` to `Released` (double-release) or from `Invalid` to `Use` (use-after-free) triggers the bug report.

- **Cross-reference**: See `docs/csa_checker_patterns.md` §3.2 (ownership tracking via region-state maps), §4.2 (paired-API matching), and §5.1 (escape analysis for resources passed to opaque callees). For lock/unlock checkers, also reference §6.1 (lock-gate tracking via `check::BranchCondition`).

## 3. Known High-Frequency False Positive Patterns

- **Resource handed off to opaque framework**: The resource is passed to a library function, callback registration, or queue that takes ownership. The checker cannot see the eventual release. Mitigation: model well-known POSIX/library sinks (`pthread_create`, `atexit`, `thrd_create`, `g_list_append`) in a built-in escape-whitelist. For unknown callees, suppress warnings when the resource handle is passed by pointer to an external function and not returned.

- **Cleanup via `cleanup` attribute / `defer`**: GCC/Clang `__attribute__((cleanup(...)))` or C++ scope guards (`std::unique_ptr`, `std::lock_guard`) handle release implicitly. The checker must recognize these and suppress bare-pointer warnings on variables with cleanup attributes.

- **Intentional process-termination path**: `abort()`, `exit()`, `_exit()` called immediately after resource acquisition without release. The OS reclaims all resources on termination. Mitigation: recognize `[[noreturn]]` functions and suppress leak reports on paths that unconditionally terminate.

- **Reference-counted objects in manually managed code**: The analyzer sees an `AddRef` but no matching `Release` in the current TU because the release happens in a different translation unit or callback. Mitigation: require paired refcount operations to be visible within the same function or explicitly annotate refcount-returning APIs.

- **Static resource pools / caches**: Resources allocated at init time and held for the program lifetime (never explicitly freed). The analyzer flags them as leaks. Mitigation: suppress warnings when the only reference is via a `static` or `global` pointer that lives until `main()` returns.

## 4. Generic Discriminant Features

- **Textbook (pure CWE-399)**: A single acquisition point with a clear paired-release function, but one control-flow path skips the release entirely. The resource handle remains in scope — the fix adds a `free()`/`close()`/`unlock()` call on the missing path. No aliasing, no opaque callees, no reference-counting ambiguity.

- **Variant 1 — Double-release (CWE-415 / CWE-1341)**: The fix replaces one of the release calls with `NULL`-assignment or adds a guard (`if (p) { free(p); p = NULL; }`). The root cause is two cleanup paths that both attempt to release the same handle. Classify primarily as double-free, secondarily as CWE-399.

- **Variant 2 — Use-after-free / use-of-expired (CWE-416 / CWE-910)**: The fix reorders operations: the release is moved after the last use, or a dangling pointer is nullified. The checker must differentiate between *missing* release (leak) and *too-early* release (UaF). These are mutually exclusive in the fix: the former adds a release, the latter delays or removes one.

- **Variant 3 — Reference-count mismatch (CWE-911)**: The fix adjusts a `refcount_inc`/`refcount_dec` or `AddRef`/`Release` call pair. The resource lifetime is managed via an integer counter that the checker cannot easily evaluate. Requires specific refcount-modeling logic (increment/decrement events tracked as symbolic integers).

- **Verdict rule**: If the resource handle is local, has a known paired-release function, and one path omits the release → **high confidence CWE-399** (leak variant). If the handle is shared (globals, aliased pointers, refcounted) or the release happens in a different scope → **lower confidence**; classify by the specific mismanagement pattern (double-free, UaF, refcount) rather than the generic category.
