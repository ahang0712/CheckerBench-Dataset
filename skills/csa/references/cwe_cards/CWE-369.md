# CWE-369: Divide By Zero
> Tier: 2 | Global samples: 30

## 1. Typical Code Patterns

Divide-by-zero defects occur when an integer or floating-point denominator is (or can become) zero at runtime. In C/C++ codebases, the most common manifestations are:

- **Direct literal division by zero** — `x / 0` or `x % 0` in code (rare in shipped code, more common in macros or generated code).
- **Unchecked user input or network-derived values** used as divisors without validation, e.g., `count / len` where `len` comes from a message header.
- **Pointer / array-length derived divisors** — `size / (width - offset)` where `offset > width` causes underflow to zero or a negative value interpreted as zero.
- **Loop-counter or index-based divisors** after a loop that may execute zero times, e.g., `total / count` computed after a conditional accumulation.
- **Reassignment / aliasing** — a divisor variable that is checked before one use but subsequently modified or aliased before another use.
- **Implicit conversion from negative to large unsigned zero** — `int d = f() - g();` where `d` may be negative, then used as `x / (unsigned)d` producing a huge unsigned divisor (not zero — covered by CWE-191), or `d` is zero and then cast.

Integer division by zero is undefined behavior in C/C++ (C99 §6.5.5, C++ [expr.mul]). Floating-point division by zero is well-defined in IEEE 754 (±inf) but is still treated as a defect by many coding standards (MISRA, JSF++) and is in scope for this CWE.

## 2. CSA Checker Architecture Recommendations

- **Base class**: `BuiltinBugChecker` (no need for `Checker<check::PreStmt>` specialization; use `check::PreStmt<BinaryOperator>` or `check::PostStmt<BinaryOperator>`).
- **Callback**: `check::PreStmt<BinaryOperator>` — inspect the RHS (divisor) before evaluation to avoid relying on folded constants from the CFG. For integer division, check before evaluation; for floating-point, check either pre or post with a configuration flag.
- **Tracking granularity**: Simple **value-constraint + taint** approach:
  1. Is the divisor a concrete `0` (intentional or from macro expansion)? Report.
  2. Is the divisor tainted (sink = division, source = user input / network / file)? Report with a taint trace.
  3. Does the divisor have a known non-zero constraint from a preceding `assume` or branch? Suppress.
- **Cross-reference**: See `csa_checker_patterns.md` §"Taint-tracking checkers" and §"Null-or-zero checkers". For FP mitigation strategies, see §"Suppression via equality-based assumptions".
- **Optional**: A separate `FloatDivByZero` checker can be toggled independently since the severity differs between integer (immediate UB) and float (defined but likely unintended).

## 3. Known High-Frequency False Positive Patterns

1. **Defensive rounding divisors** — `value / (denom == 0 ? 1 : denom)` . The ternary guard is visible syntactically; the checker must recognize this pattern and suppress.
2. **Static array `sizeof` divisors** — `sizeof(arr) / sizeof(arr[0])`. Both operands are positive constants; the checker must suppress when both are compile-time constants > 0.
3. **Loop-constant divisors** — `for (int i = 0; i < N; i++) { … x / i … }` where the first iteration `i == 0` triggers a report. Suppress when the divisor is a loop induction variable and the expression is unreachable on the first iteration (e.g., `i > 0` guard) or when the division is inside a conditional `if (i != 0)`.
4. **Unreachable-path divisors** — `if (p) { *p = 0; } else { x / *p; }` where the path with zero divisor is actually unreachable due to a null check. The checker must respect path sensitivity.
5. **C++ template instantiations with zero arguments** — `Divide<0>::apply(x)` where the template parameter guarantees zero. Suppress if the path is known-unreachable after template instantiation.
6. **Macro-generated zero divisors in configuration headers** — `#define DIV 0` used in dead code paths. Checker should suppress if the macro expansion is inside an `#if 0` or equivalent dead block.

## 4. Generic Discriminant Features

**Textbook (obvious) variants:**
- Literal `0` as the divisor in `BinOp` / `CompoundAssignOp`.
- Divisor is a declared `const` / `constexpr` variable initialized to `0`.
- Divisor is the return value of a function that unconditionally returns `0`.
- Divisor is uninitialized stack memory (`x / uninit_var`).

**Variant / borderline cases (may require contextual reasoning):**
- Divisor that is zero only on a subset of paths (path-sensitive analysis needed).
- Divisor that is the result of an underflow: `x / (a - b)` where `a < b` produces a large unsigned value (not division-by-zero but CWE-191; however if `a == b` exactly, it *is* division-by-zero).
- Floating-point division by zero where the result is immediately passed to `isfinite()` or compared to `INFINITY` — intentionally used.
- Divisor from a volatile read — the compiler cannot fold it, but the value may provably never be zero on the target hardware (cannot prove generically; suppress if volatile).
- Division in unreachable code (dead branch, `if (false)`, etc.) — checker must gate on reachability.
