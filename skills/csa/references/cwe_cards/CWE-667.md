# CWE-667: Improper Locking
> Tier: 2 | Global samples: 49 | ⚠️ Extreme kernel bias (≥96%) — userspace applicability unverified

## 1. Typical Code Patterns

Improper locking arises when thread-shared state is accessed without correct
lock acquisition or release. In C/C++ kernel code the dominant patterns are:

- **Unlocked access to spinlock‑/mutex‑protected fields**  
  A struct field is always read/written under a specific lock, but one code
  path touches it without holding that lock. Often detected by pairing a
  `spin_lock` / `mutex_lock` call with an access and flagging paths where the
  lock was never acquired.

- **Incorrect unlock on error paths**  
  A lock is acquired, then a conditional branch (e.g., `if (error) return -E;`)
  skips the matching `spin_unlock` / `mutex_unlock`. This leaves the lock held,
  causing potential deadlock on the next acquisition attempt.

- **Double‑lock / deadlock**  
  The same lock is acquired twice without an intervening release on the same
  thread (e.g., calling `mutex_lock(L)` inside a helper that is called while
  `L` is already held). Also includes AB‑BA deadlock where two locks are
  acquired in inconsistent order across threads.

- **Lock‑class confusion**  
  A function parameter or global pointer can refer to one of several distinct
  locks, and the checker cannot statically determine which lock protects a
  given access. Common when a “lock” member of a structure is used
  interchangeably with a different lock in another struct.

No dynamic annotation (e.g., `__attribute__((acquired)))`) is needed for
detection, but its absence limits recall.

## 2. CSA Checker Architecture Recommendations

- **Base class:** `BugChecker` + `CheckPreCall`, `CheckPostCall`, and
  `checkEndFunction` / `checkDeadSymbols` for cleanup.
- **Tracked state per lock:** a map from lock expression → holder-tag or
  “locked count”. For recursive locks maintain a depth counter.
- **Tracking granularity:** function‑level or basic‑block‑level is sufficient;
  cross‑function tracking via `ProgramState` `removeDeadBindings`.
- **Core heuristic:** when a call whose name matches a known lock/unlock
  pattern (`*_lock`, `*_unlock`, `spin_lock`, `mutex_lock`, etc.) is seen,
  update state. On every memory store/load to a field that has an associated
  lock annotation (or convention), check whether the owning lock is held.
- **Cross‑reference:** see `csa_checker_patterns.md` §“Lock‑tracking checkers”
  for the `CallDescription` lock‑pattern registry and `ProgramState` trait
  pattern.

## 3. Known High-Frequency False Positive Patterns

- **Lock taken in caller, callee accesses protected data**  
  The checker loses track when the lock is acquired in an inlined or
  out‑of‑line parent frame. Mitigate with a small stack of “locks held”
  that persists across call boundaries unless the callee is known to drop
  them.

- **RCU / read‑side critical sections**  
  Kernel RCU (Read‑Copy‑Update) does not use explicit spinlocks; the checker
  flags RCU‑protected reads as unlocked. Suppress by whitelisting
  `rcu_read_lock` / `rcu_read_unlock` as valid lock primitives, or exclude
  RCU‑only paths.

- **Per‑CPU variable access**  
  Disabling preemption (`preempt_disable`) is the implicit “lock” for
  per‑CPU data. False positives arise unless `preempt_disable/enable` are
  modelled as lock/unlock operations.

- **Lock‑free / atomic access idioms**  
  `READ_ONCE` / `WRITE_ONCE` and atomic RMW operations intentionally avoid
  locks. These should be treated as safe accesses; whitelist `atomic_*` and
  `__READ_ONCE` / `__WRITE_ONCE`.

## 4. Generic Discriminant Features

| Textbook violation | Variant / low‑severity |
|---|---|
| Lock not held on *any* path to access | Lock held on most paths but dropped on one rare error branch (still a bug, but often lower impact). |
| Same lock acquired twice (deadlock) | Same lock acquired twice because the function is called recursively — only a bug if the lock is non‑recursive. |
| Plain store without lock | Store via `atomic_set` or with `WRITE_ONCE` — usually intentional. |
| Unlock without matching lock in same function | Unlock in a cleanup helper that is called only when the lock was acquired by the caller — not a defect. |
