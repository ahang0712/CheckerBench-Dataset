# CWE-415: Double Free
> Tier: 2 | Global samples: 67

## 1. Typical Code Patterns

A double free occurs when `free()` (or `delete`/`free()` on the same raw pointer) is called more than once on the same heap-allocated memory block without an intervening reallocation. The most common manifestations in C/C++ codebases are:

- **Error-handling double release:** A pointer is freed inside a loop or conditional branch, then freed again on an error-exit path that duplicates cleanup logic. Example pattern: `free(p); return -1;` in one branch, followed later by `free(p);` after the conditional block.

- **Missing pointer nullification after first free:** The pointer is freed, but the variable is not set to NULL. Later code checks `if (ptr)` (believing NULL indicates "already freed") and calls `free(ptr)` again, unaware the pointer is stale.

- **Shared-ownership confusion:** Two components both believe they own the pointer. One frees the memory; the other frees it again (common in legacy C code without clear ownership semantics).

- **Double-free via `realloc` failure:** The result of `realloc(p, new_sz)` is assigned to `p` directly. If `realloc` fails and returns NULL, the original block is leaked—but if a second code path later frees the original pointer (now NULL or stale), a double free can arise.

- **Destructor + explicit delete in C++:** A class destructor deletes a member pointer, and calling code also explicitly `delete`s that same pointer afterward.

All patterns share the root cause: loss of **unique ownership tracking** at the point of the second free.

## 2. CSA Checker Architecture Recommendations

- **Base class:** Implement `Checker<check::PostStmt<CallExpr>>` (or `check::PreStmt` for interleaved checks) with optional `check::DeadSymbols` for state cleanup.

- **Callbacks:** Intercept calls to `free()`, `realloc()`, `delete`, and `delete[]`. Use `check::PreStmt` to inspect the argument *before* it is consumed by the deallocation routine.

- **Tracking granularity:** Attach a **symbolic state trait** to each `MemRegion` or `SymbolRef` that records the deallocation status as `{Allocated, Freed, Escaped}`. Transition `Allocated → Freed` on first deallocation; flag a report if a deallocation is attempted when the state is already `Freed`.

- **Cross-reference to `csa_checker_patterns.md`:** Follow the "Path-Sensitive Malloc Checker" pattern. Use `ProgramStateRef` to map `SymbolRef` → a custom `RefCount` structure. Model `free` as a `check::PostStmt` that kills the symbol's binding and updates the trait.

- **Inter-procedural hints:** For functions that "take ownership" (e.g., `list_add`), model the transfer via a checker callback to prevent false positives from intentional transfers.

- **No alias-hungry tracking needed:** CSA's built-in region-store symbolic tracking is sufficient; you do not need full points-to analysis because double-free is a path-local, flow-sensitive flaw.

## 3. Known High-Frequency False Positive Patterns

- **Custom allocator wrappers:** Projects wrap `free()` in a macro or inline function (e.g., `XFREE(p)` that nullifies the pointer). The CSA sees the inner `free()` call and, if the wrapper is not modeled, assumes the pointer is double-freed on a subsequent path. Mitigation: model the wrapper via checker options or inline its semantics.

- **Glue-code null-check idioms:** `if (p) { free(p); p = NULL; }` followed by a second `if (p) { free(p); }`. If state-splitting does not propagate the null assignment precisely, the analyzer may report the second free as reachable.

- **C++ smart-pointer interop:** When `std::unique_ptr` wraps a raw pointer that is also freed in a destructor. The analyzer may double-count the deallocation if the raw-raw pointer escapes the smart pointer's scope.

- **`realloc` success-path false positive:** Code frees the old pointer only on `realloc` failure (common pattern: `new_p = realloc(p, sz); if (!new_p) { free(p); return; } p = new_p;`). If the checker does not mark the failure-path free as exclusive, it can wrongly trace a path where the old pointer is freed twice.

- **Pool / arena allocators:** Memory managed by a region-based allocator that never calls `free()` on individual blocks, but the checker sees only the `free()` calls on the pool itself. Enabling the checker only on selected alloc families reduces noise.

## 4. Generic Discriminant Features

- **Textbook** (single path, straightforward):
  - Free in same function, same basic block or adjacent blocks.
  - No intervening aliasing or pointer arithmetic on the freed pointer.
  - No conditional logic that could make the second free unreachable in practice.
  - `double-free()` symbol reported directly by UndefinedBehaviorSanitizer (UBSan) at runtime.

- **Variant** (multi-path or aliased):
  - The two frees occur on distinct execution paths that converge (e.g., error label + normal cleanup).
  - The freed pointer is reachable through an alias that is freed independently.
  - A `realloc` or custom allocator reintroduces the same logical address on a different symbolic path.
  - One free occurs in a destructor invoked implicitly (C++ RAII) and the other explicitly.

- **Judgment rules:**
  1. If both frees lie on **all** paths from allocation to function exit, it is a definite bug; report at Tier 1 priority.
  2. If the second free is guarded by a condition that is always true when the first free executed (path convergence), it is still a true double-free—report it.
  3. If an alias passes through a function that does not have a summary (opaque callee), downgrade to a **warning** with a note advising a manual inspection.
  4. If the pointer is re-assigned (allocated again) between frees, it is **not** a double free—suppress.
