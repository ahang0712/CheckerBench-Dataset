# CWE-772: Missing Release of Resource after Lifetime
> Tier: 2 | Global samples: 27

> ⚠️ **Distribution warning:** Over 96% of samples are from userspace projects — kernel applicability is unverified.

## 1. Typical Code Patterns

Resource lifetime mismanagement in C/C++ manifests in four dominant patterns:

- **Dynamic memory never deallocated:** `malloc()`/`calloc()`/`realloc()`/`new` without a matching `free()`/`delete` on all paths. Typical in error-handling paths where a `goto cleanup` pattern is missing or an early `return` bypasses `free()`.

- **POSIX/OS handle leaks:** `open()` → missing `close()`, `fopen()` → missing `fclose()`, `socket()` → missing `close()`, `accept()` → missing `close()`. Often occurs when a function acquires a resource in a loop and one iteration returns early without releasing the previous handle.

- **Lock/unlock asymmetry:** `pthread_mutex_lock()` / `pthread_rwlock_rdlock()` without a matching unlock on every exit path. Critical in functions with multiple `return` statements.

- **Descriptor handoff ambiguity:** Creating a resource (e.g., `dup()`-ed fd, `asprintf`-allocated buffer) and relying on the caller to free it, but the contract is undocumented or inconsistent.

## 2. CSA Checker Architecture Recommendations

- **Base class:** `BuiltinBugChecker` with `checkDeadSymbols()` or `checkEndFunction()` for tracking outstanding resources at function exit; `checkPreCall()`/`checkPostCall()` for acquire/release pairing.
- **Tracking granularity:** Use `ProgramStateRef` to maintain a `ResourceSet` (e.g., `llvm::ImmutableSet<SymbolRef>`) of still-held resources. Bind acquire calls to `set` insertion; release calls to `remove`. A non-empty set at `checkEndFunction` (excluding main) or `checkDeadSymbols` triggers the warning.
- **Callbacks critical:** `checkPostCall` — tag the return symbol as an acquired resource; `checkPreCall` — match known release functions and remove from set; `checkEndFunction` — emit report if set is non-empty (with escaped-resource suppression).
- **Cross-reference:** See `csa_checker_patterns.md` §3.3 (stateful resource tracking pattern) and Appendix A.1 for `checkDeadSymbols` vs. `checkEndFunction` trade-offs.

## 3. Known High-Frequency False Positive Patterns

- **Resource stored/escaped into global state or caller-owned structure:** The checker cannot prove the resource outlives the function intentionally (e.g., storing an fd into a struct field, inserting into a global list).
- **RAII wrappers / custom smart pointers:** Stack-allocated objects that call `free` in their destructor are invisible to a simple acquire/release matcher unless the checker understands the wrapper semantics.
- **Resource handoff across library boundaries:** `getenv()`, `strdup()` contract confusion — the caller may or may not own the returned pointer.
- **Failure-case short-circuit macros:** `#define CHECK_AND_RETURN(x) if (!x) return` — macro expansion hides the fact that a resource is released before the return.
- **Threaded / signal-handler release:** Releases happening in another thread or in a signal handler are invisible to path-sensitive analysis.

## 4. Generic Discriminant Features

| Textbook CWE-772 | Variant / False Positive |
|---|---|
| `malloc()` with NO `free()` on any path, function returns | Resource escaped via `return ptr` to caller (API contract) |
| `open()` in loop body, `close()` missing on error path | Resource stored in struct/global — release deferred |
| Mutex locked at function entry, only one `return` calls `unlock` | RAII wrapper (`lock_guard`) owns release via destructor |
| `asprintf` / `strdup` in argument — leaked if second arg evaluation short-circuits | Resources freed in a different function (file close via `fcloseall`) |
| Resource acquired but released only in `#ifdef DEBUG` blocks | Thread-handoff: child thread closes fd after parent returns |

The core heuristic: **does every statically reachable path from acquisition to function exit (or scope exit) contain a release operation on the exact same resource?** If no, classify as textbook; if the resource escapes into opaque state or is managed by a destructor the checker cannot model, classify as variant/FP.
