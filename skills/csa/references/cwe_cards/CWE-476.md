# CWE-476: NULL Pointer Dereference
> Tier: 1
> Global samples: 447 | Variant samples: 447 | Source projects: 64

## 1. Typical Code Patterns

NULL pointer dereference in C/C++ occurs when a pointer that is (or may be) null is used as the target of a read or write operation without a prior null check. This is among the most prevalent memory safety issues in C and C++ codebases. In real-world C/C++ code, the pattern commonly appears in the following forms:

- **Unchecked allocation return value:** A memory allocation function (`malloc`, `calloc`, `realloc`, `kmalloc`, `kzalloc`, `new`) returns NULL to indicate failure, but the caller dereferences the return value before testing it. This is the single most common manifestation: `buf->field = val` immediately after `buf = malloc(size)` with no `if (!buf) return -ENOMEM;` guard.

- **Unchecked function return value:** A function that can return NULL on error (e.g., `strdup`, `strndup`, `fopen`, `mmap`, `memalign`, `rb_find`, `list_first_entry_or_null`, a lookup or search function) is called and its result is dereferenced without checking for NULL. The nullability of the return is documented but not enforced at the call site.

- **Assumed-non-null after a partial check:** Code tests `if (ptr)` at one point, performs operations under that guard, but then exits the guarded scope and dereferences `ptr` later under the assumption it is still non-null, without an intervening check. A common variant: checking `ptr` for one purpose (e.g., "is this feature enabled?") and then using it for a different purpose (e.g., "access this data structure") without re-verification.

- **NULL-returning lookup in container/iterator patterns:** A function searches a data structure and returns NULL when the key is not found (e.g., `ht_lookup(key)`, `idr_find(id)`, `list_first_entry_or_null`), but the caller assumes the lookup always succeeds and immediately dereferences the result.

- **String operation on NULL:** Functions from `<string.h>` (e.g., `strlen`, `strcpy`, `strcmp`) are called with a pointer that is NULL on some execution path. Since the C standard library does not define behavior for NULL string arguments, this results in a crash when the implementation attempts to read from address zero.

- **Function pointer call through unchecked pointer:** A function pointer stored in a struct or global table is invoked without checking whether it is NULL. This typically appears in driver dispatch tables, callback registration mechanisms, or plugin-like architectures where a slot may be unpopulated.

- **IOCTL / request-handler dispatch with missing null verification:** In kernel or service code, an input message carries an optional pointer field that is assumed to be valid based on a flag, but the flag and the pointer are not validated atomically; a race or malformed input leaves the pointer NULL while the flag indicates it should be valid.

- **Short-circuit evaluation ordering defect:** A condition like `if (ptr && ptr->field)` is correctly guarded, but later in the same function the logic is restructured and the guard is lost: `if (other_condition) { ptr->field = val; }` where `ptr` could be NULL on the path that reaches that branch.

## 2. CSA Checker Architecture Recommendations

- **Checker base class:** `ento::Checker<check::Location>` is the primary callback for detecting dereferences of tracked null pointers. Complement with `check::PreCall` to detect null pointers passed as arguments to known non-null-expecting functions (e.g., `memcpy`, `strlen`), and `check::PostCall` to track returned-null-or-nullable from allocation and lookup functions.

- **SymbolRef / ProgramState granularity:**
  - Maintain a `REGISTER_SET_WITH_PROGRAMSTATE(NullSymbols, SymbolRef)` tracking pointer symbols that are constrained to null on the current path. When a pointer symbol is in this set, any dereference (load/store to its pointee) via `check::Location` constitutes a bug.
  - Alternatively, for richer state, use a `REGISTER_MAP_WITH_PROGRAMSTATE(PtrNullState, SymbolRef, NullabilityTag)` where `NullabilityTag` enumerates `{NonNull, Nullable, Null, Unknown}` — this mirrors the approach used by the NullabilityChecker and allows merging of nullness information across paths.
  - Use a second set or map to track pointers that were returned from known-allocator functions but whose return value was not checked. This "unchecked allocation" set catches the most common CWE-476 pattern and can be checked at `check::Location` or at the next `check::PreCall` that uses the pointer.
  - Use `eval::Assume` to detect when a previously non-null pointer becomes constrained to null (indicating a separate null-assignment or failed-allocation path), and add it to the null-tracking set.

- **Cross-reference patterns in `references/csa_checker_patterns.md`:**
  - **Pattern 4 (Null Checking / Nullability Propagation)** — the primary structural reference. The NullabilityChecker's architecture of tracking nullability state per `MemRegion`, using `check::Location` for dereference detection, and leveraging `eval::Assume` for inference is directly applicable. The callback set (`check::PreCall`, `check::PostCall`, `check::Location`, `eval::Assume`, `check::DeadSymbols`) should be adapted for the simpler null-deref-only use case.
  - **Pattern 3 (Resource Tracking — SimpleStreamChecker)** — for the allocation-return-value tracking pattern specifically. Model allocation calls (`malloc`, `kmalloc`, `strdup`) as producing a symbol that starts in "unchecked" state, then at each use of that symbol, verify either (a) it has been null-checked on this path or (b) it is known-non-null. This is simpler than full resource tracking since no release semantics are needed.
  - **Pattern 5 (Complex Resource Tracking with SymbolRef Maps — MallocChecker)** — for the `eval::Assume` pattern that handles failed-allocation paths. When a pointer symbol from an allocation is assumed NULL in a branch condition (e.g., `if (!ptr)`), the checker should use that assumption to avoid reporting on the false branch, and conversely should warn on the true branch if the pointer is dereferenced without recheck.

- **Constraint-based detection (simpler alternative):** For a lightweight checker, use only `check::PreStmt<BinaryOperator>` and `check::PreStmt<MemberExpr>` (for `->` field access) combined with `State->isNull(ptrVal)` and `ConstraintManager::assumeDual`. When a pointer is constrained null on the current path, the dereference is a bug. This avoids the complexity of program-state maps but also misses patterns where the null-check is done after the assignment (non-SSA issues). Recommended only for Tier 1 coverage if full path sensitivity is not required; otherwise, prefer the state-tracking approach.

## 3. Known High-Frequency False Positive Patterns

The following situations inherently produce false positives for a path-sensitive null-dereference checker. These arise from the gap between the analyzer's conservative model and real-world coding idioms:

- **Assertion-based contracts:** Many C/C++ codebases use `assert(ptr != NULL)` before dereferencing. The Clang Static Analyzer does not interpret `assert` as a constraint — assertions are compiled out in release builds and the analyzer typically does not evaluate them. When a pointer is dereferenced immediately after an `assert`, the analyzer sees a path where `ptr` could still be null. **Suppression:** Teach the checker to recognize `assert` expressions (and custom assertion macros registered via `check::PreCall` or `check::BeginFunction`) as implicit constraints. Alternatively, use the `analyzers-opt` `-analyzer-config` to treat `assert`-like functions as CFG sinks.

- **Guard variable idiom:** Code uses a separate boolean variable (`int buf_initialized = 0;`) to indicate that a pointer has been allocated. The analyzer cannot always prove the logical relationship between the guard flag and the pointer's nullness — it tracks the flag as a separate `SymbolRef` and may not merge the two constraints. **Suppression:** Implement a `check::Bind` callback that, when a pointer is assigned to a global/static variable alongside a guard flag, records the dependency as an invariant in `ProgramState`. At dereference sites, check whether the guard flag is constrained true on the current path; if so, suppress the warning. Alternatively, rely on the existing `check::DeadSymbols` to remove stale constraints and accept the remaining FPs as a known limitation.

- **Deferred allocation pattern (lazy init):** A pointer is declared as NULL, various code paths test `if (!ptr) ptr = allocate()`, and one path dereferences `ptr` before the allocation runs. The analyzer may explore paths where the allocation has not yet been called. The checker cannot distinguish "the programmer forgot to allocate" from "the analyzer chose an infeasible path order." **Suppression:** At `check::BeginFunction`, initialize the null-tracking state to all function-scope pointers. If a pointer is accessed before any allocation call on a path, the warning is legitimate; but if the path order is infeasible, the user will see an FP. Reduce this by checking whether the pointer symbol is alive (has been written to) before reporting.

- **Sentinel-terminated data structure traversal:** A loop walks a linked list or tree using a sentinel (e.g., `while (cur) { cur = cur->next; }`) and the last iteration correctly exits because `cur` becomes NULL. A checker that fires on `cur->next` inside the loop would be incorrect because the loop condition ensures `cur` is non-null at each entry point. **Suppression:** The existing CFG-based analysis should already handle this correctly (the loop condition is evaluated before the body), but the checker must ensure it evaluates the dereference *after* the null check, not before. Use `check::Location` rather than `check::PreStmt<MemberExpr>` to let the CFG order correctly reflect the loop guard.

- **`__attribute__((nonnull))` not consistently used:** Some function parameters are documented as non-null by convention but lack the `__attribute__((nonnull))` annotation. The checker may emit a report when a nullable pointer is passed to such a function even though the programmer considers this path infeasible. **Suppression:** When `check::PreCall` detects a mismatch between a pointer's nullability state and the function's expected contract, use the nullability annotation (if present) to decide. If the annotation is absent, fall back to the pointer's tracked state and emit only if the pointer is definitively null (not just nullable).

- **`realloc` semantics confusion:** `realloc(ptr, size)` returns NULL on failure while leaving the original `ptr` allocated. Code that writes `ptr = realloc(ptr, new_size); ptr->field = val;` has a double bug (leak + null deref). However, code that uses a temporary (`new_ptr = realloc(ptr, size); if (!new_ptr) ...; ptr = new_ptr;`) is correct, but a checker may still warn on the reassignment path if it loses track of the null check. **Suppression:** Treat `realloc` specially: when the return value is assigned to the same variable as the input argument, flag it immediately as suspicious. When a temporary is used, track the null-check on `new_ptr` before the reassignment to `ptr`.

- **Dead code in conditional compilation (`#ifdef` / `#if`):** The analyzer sees all branches of preprocessor conditionals within a single translation unit. A dereference guarded by `#ifdef HARDWARE_PRESENT` will still be analyzed and potentially reported if the pointer could be null on a different `#ifdef` path. **Suppression:** Inline suppression via `__attribute__((analyzer_noreturn))` or `-analyzer-config` `suppress-null-return-paths=true`. For project-wide suppression, maintain a list of known-safe pointer sources (e.g., `this`, `__get_free_page`, `kstack`) that are never null.

## 4. Generic Discriminant Features

The following features help distinguish a textbook CWE-476 null pointer dereference from variants and hybrid weaknesses:

- **Allocation-to-dereference distance:** Textbook CWE-476 has a short causal chain: `ptr = alloc(); ptr->field = val;` with no null check in between. If the null check exists but is ineffective (e.g., checks a different variable, or checks after the first use), the bug is still textbook CWE-476. If the null originates from an entirely different function many call frames away, the bug may involve missing error propagation (CWE-252 / CWE-755) rather than a direct null dereference.

- **Null origin classification:**
  - *Allocation failure* (return from `malloc`/`kmalloc`/`calloc`) → textbook CWE-476.
  - *Lookup miss* (return from `ht_find`/`idr_find`/`strchr`/`strstr`) → textbook CWE-476, but often co-occurs with missing error handling (CWE-252).
  - *Null assigned by a prior code path* (e.g., `ptr = NULL` in an error branch, then a common exit dereferences it) → still CWE-476, but may be interleaved with control-flow issues (CWE-670 / CWE-404).
  - *Null from an uninitialized variable* (never assigned before use) → closer to CWE-457 (Use of Uninitialized Variable) rather than CWE-476; the dereference is a consequence rather than the root cause.
  - *Null from a race condition* (one thread clears a pointer while another dereferences it) → CWE-476 + CWE-362 hybrid; the fix typically requires locking, not just a null check.

- **Dereference surface area:**
  - *Direct member access* (`ptr->field`) → classic CWE-476.
  - *Array subscript* (`ptr[i]`) → still CWE-476, but may also involve out-of-bounds write (CWE-787) if the null is treated as address zero and the offset is non-zero.
  - *Function pointer call* (`ptr->func()`) → CWE-476, but the impact is control-flow hijacking rather than just denial of service; may be classified as CWE-822 (Untrusted Pointer Dereference) if the pointer value is attacker-controlled and non-null.
  - *Memory copy* (`memcpy(ptr, src, n)`) → CWE-476 if `ptr` is null, but often classified as CWE-119 or CWE-120 if the root cause is an unchecked size.

- **Fix pattern:** A textbook CWE-476 fix adds a single `if (!ptr) return -ENOMEM;` (or equivalent) guard before the dereference. If the fix instead changes an allocation to `GFP_KERNEL` (never-fail variant), adds a `__must_check` attribute, or restructures control flow to avoid the path that reaches the dereference with null, the bug may be an intentional design assumption violated by a particular caller (closer to CWE-690: Unchecked Return Value).

- **Multiple dereferences in the same function:** If the same null pointer is dereferenced many times in one function, it is likely a single missing null check at the function entry or after allocation (one bug, multiple crash sites). If different pointers are null on different paths, these are independent bugs that should be analyzed separately. A checker should group reports by the null-assigning location to avoid flooding the user with duplicate reports for the same root cause.
