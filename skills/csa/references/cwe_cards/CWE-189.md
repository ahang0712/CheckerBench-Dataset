# CWE-189: Numeric Errors
> Tier: 2 | Global samples: 36

> ⚠️ **Distribution warning:** Over 100% of samples are from userspace projects — kernel applicability is unverified.

## 1. Typical Code Patterns

CWE-189 is a category umbrella for weaknesses involving improper calculation or conversion of numbers. In C/C++ codebases, the most common manifestations fall into four groups:

**Integer overflow/wraparound (CWE-190).** An arithmetic operation (addition, multiplication, increment) produces a result exceeding the target type's range. The overflowed value is used as an allocation size, array index, or copy length. Classic example: `size_t total = count * sizeof(T)` where the product wraps, producing a small `total` that passes a safety check but undersizes an allocation.

**Integer underflow (CWE-191).** A subtraction or decrement produces a value below the type's minimum. Common in size computations: `remaining -= consumed` when `consumed > remaining`, wrapping to a huge positive value. Often leads to buffer over-read or infinite loop in parsing code.

**Incorrect numeric conversion (CWE-681).** A value of one integer type is implicitly or explicitly converted to a different type with different range or signedness. Truncation (narrowing) discards high-order bits; sign-extension of a negative signed value into an unsigned type produces a large positive value. This appears at API boundaries where parameter types mismatch.

**Division by zero (CWE-369) and off-by-one (CWE-193).** Division or modulo with a denominator that can be zero, or fencepost errors where loop bounds or length comparisons are off by one.

Across all subtypes the recurring mechanism is: **untrusted or unvalidated input reaches a numeric operation whose result controls a security-relevant decision** — allocation size, memory offset, loop bound, or buffer length.

## 2. CSA Checker Architecture Recommendations

- **Base class:** `Checker` with `check::PreStmt<BinaryOperator>` (for overflow/underflow in arithmetic), `check::PreCall` / `check::PostCall` (for division, type conversion at function boundaries, and allocation-size validation), and optionally `check::Location` for off-by-one access patterns. For divide-by-zero specifically, follow the `DivZeroChecker` pattern (single `check::PreStmt<BinaryOperator>` callback; see pattern 1 in `csa_checker_patterns.md`).
- **Tracking granularity:** Maintain a `SymbolRef`-based map in `ProgramState` recording the **signedness and width** of each integer symbol, plus a **taint tag** marking values from untrusted sources. Track the **symbolic expression tree** of computed values so the checker can distinguish guarded operations (`if (x < LIMIT) x + 1`) from unguarded ones.
- **Callbacks:** `checkPreStmt<BinaryOperator>` to inspect `BO_Add`, `BO_Sub`, `BO_Mul`, `BO_Div`, `BO_Rem`, `BO_Shl`, `BO_Shr` before evaluation; `checkPostCall` for allocation functions to validate size arguments against symbolic upper bounds; `checkPreCall` to flag division where the divisor's range includes zero.
- **Cross-reference:** See patterns **1 (division by zero)** and **2 (undefined value)** in `csa_checker_patterns.md` for the simplest checker skeletons. For overflow in allocation-size computation, adapt the **post-call-size-validation** logic from the resource-tracking patterns (patterns 3/5).

## 3. Known High-Frequency False Positive Patterns

**Saturated arithmetic as defense.** Code that performs an addition and then checks `if (result < a)` is deliberately using wraparound to detect overflow. **Mitigation:** track data-flow; if the result immediately feeds an overflow-detection comparison, suppress.

**Intentional wraparound in cryptography/hashing.** Modular arithmetic (`(a + b) & 0xFFFFFFFF`), PRNG state updates, and checksum computations rely on defined wraparound. **Mitigation:** allow project-supplied allowlists (function names, macro annotations) for known-safe arithmetic contexts.

**Unsigned decrement idioms.** `while (n--)` and `for (size_t i = len; i > 0; i--)` wrap from 0 to `SIZE_MAX` intentionally. **Mitigation:** suppress when the overflowed value is used only as a loop condition, never dereferenced or passed to allocation.

**Truncation at known-safe boundaries.** A `uint64_t` truncated to `uint32_t` when the value is proven ≤ UINT32_MAX by prior checks. **Mitigation:** integrate with `RangeConstraint` — emit only when the symbolic range exceeds the target type's capacity.

**sizeof and constant-foldable operations.** Arithmetic on compile-time constants appears in the AST but is provably safe. **Mitigation:** evaluate constant expressions at analysis time; warn only when at least one operand is a runtime symbol with a plausible overflow range.

## 4. Generic Discriminant Features

**Textbook CWE-189** (high confidence, pure instance):
1. Short data-flow: **untrusted source → single numeric operation → security-sensitive sink** (allocation, index, copy length, divisor).
2. No intervening bounds check on the operands — or a check using an incorrect type (e.g., comparing `size_t` against a signed `int` maximum).
3. The result is used directly without clamping, modulo, or saturation.
4. The operation is a simple addition, subtraction, multiplication, or division — the simplest cases are the most reliably exploitable.

**Variant or hybrid** (lower confidence, mixed CWE):
1. The numeric error occurs after multiple operations and type conversions, requiring deep symbolic expression tracking.
2. Partial sanitization exists — one operand is checked but not the other, or a related-but-different value is validated.
3. The numeric error enables a downstream CWE (heap overflow via undersized allocation, out-of-bounds write via truncated index). The primary bug class may be the memory safety violation, not the arithmetic itself.
4. Intentional wraparound idioms (saturation, cryptography, PRNG) — classify as non-vulnerable upon recognition.
5. Multi-step protocol or format parser where the error only manifests for crafted sequences of inputs, not a single value.
