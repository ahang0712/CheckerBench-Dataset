# CWE-908: Use of Uninitialized Resource
> Tier: 2 | Global samples: 26

## 1. Typical Code Patterns

**Most common in C/C++ codebases:**

1. **Stack variable never assigned before first read** — declaring `int x;` and then reading `x` (or worse, `if (x)` ) without any intervening write. The value is indeterminate.

2. **Malloc-allocated heap memory read before any store** — calling `malloc(N)` and immediately dereferencing a field or element without `memset` or per-field assignment.

3. **Struct field or array element skipped during partial init** — designated initializers or piecewise assignment leave one field untouched, then that field is read later.

4. **Uninitialized pointer then dereferenced** — `int *p; *p = 42;` or passing an uninit pointer to `memcpy` / `strcpy`.

5. **Conditionally initialized variable used outside the branch** — a flag variable is set only inside `if (cond)` but read unconditionally afterward. The analyzer cannot prove the condition is always true at the use site.

6. **By-value out-parameter usage** — a function accepts a pointer parameter documented as "output only" but the caller passes a pointer to uninit memory, then reads the pointed-to value. If the callee fails to write before a certain path, the resource stays uninit.

## 2. CSA Checker Architecture Recommendations

- **Base class:** `BuiltinBugChecker` or `Checker<check::DeadSymbols, check::EndFunction, check::Location>`.
- **Core tracking mechanism:** Use a `RegionState` map keyed on `MemRegion` (not raw symbols) to track whether each region has been written to. Mark a region as "definitely written" when `checkBind` fires on any sub-region. Mark as "escaped to init function" for known-safe library calls (e.g., `memset`, `bzero`, `SecureZeroMemory`).
- **Callback for reads:** In `checkLocation` (or a `checkPreCall` on dereference), if the load targets a region with no recorded write, emit a `BugReport` with a diagnostic note tracing the allocation/declaration point and the uninit use.
- **Tracking granularity:** Field- and element-sensitive. A `struct { int a; int b; }` is fully initialized only when *both* fields have been written. An array is fully initialized when every index in the accessed range is written.
- **Handling partially initialized regions:** Use a "definitely written" / "maybe written" / "never written" lattice. Emit warnings only on "never written." "Maybe written" should be suppressed (false positive).
- **Cross-reference:** See `csa_checker_patterns.md` sections on *Region-based state* and *Partial-initialization lattices*.

## 3. Known High-Frequency False Positive Patterns

1. **Padding bytes / alignment holes** — uninitialized bytes between struct fields are impossible to write in standard C but are never read by portable code. Suppress when the load targets a `FieldRegion` known to be padding (compiler-ABI defined).

2. **Conditional init proven exhaustive by domain logic but not by AST** — e.g., `if (err) return; x = 1;` followed by `use(x);`. If the return-before-use dominates all error paths, the checker may still see an uninit path. Mitigation: track sink functions (exit, abort, longjmp) and prune infeasible paths.

3. **Volatile / MMIO regions** — memory mapped hardware registers are "initialized" by the hardware, never by software stores. Suppress all checks on `volatile`-qualified accesses.

4. **Static local with first-call init guard** — `static int x; if (!init) { x = setup(); init = 1; } use(x);` On first call, `init` is 0, so `x` is written before use. The checker may not merge the `init==1` branch correctly. Suppress when a controlling flag is checked before the use.

5. **Uninitialized in allocator wrappers / custom slabs** — application-level allocators that return memory from a reused pool whose previous content is "logically initialized" but the checker sees a fresh region with no stores.

## 4. Generic Discriminant Features

- **Textbook variant:** A local scalar or pointer declared, never written, then read in a nearby expression (within the same or immediately next statement). This is unambiguous undefined behavior.
- **Variant / borderline:** (a) Partial struct init where an unused field is read via `memcpy` of the whole struct; (b) out-of-order field init where a field is written-then-read but the checker's region state was invalidated by a function call; (c) union member read through a non-active member.
- **Rules of thumb:**
  - Single-path analysis: if the uninit read *always* follows declaration with no intervening write → textbook.
  - Multi-path analysis: if there exists *any* path from decl to use with no write → report, but mark as variant if the uninit path depends on a condition that is contradictory in practice.
  - If the resource is heap memory (`malloc`/`calloc`) → less likely to be a deliberate idiom (except with custom allocators).
  - If the resource is a struct/array → check field/element granularity; partially init is more likely variant.
- **Anti-patterns that are NOT CWE-908:** (1) Using `calloc` (always zeroed) and then complaining about zero-init; (2) reading uninitialized union padding from the non-active member (this is implementation-defined, not uninit UB); (3) reading indeterminate bytes through `char`-typed lvalue (allowed by defect reports, but still warned in practice).
