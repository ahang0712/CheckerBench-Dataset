# CWE-400: Uncontrolled Resource Consumption
> Tier: 2 | Global samples: 45

## 1. Typical Code Patterns

CWE-400 covers exhaustion of finite system resources (memory, file descriptors, sockets, threads, disk space, CPU time). In C/C++ codebases the most tractable patterns for static analysis are:

- **Unbounded memory allocation in loops**: `while(recv(...)) { buf = malloc(n); }` — allocation called inside a loop whose trip count is attacker-influenced, without a corresponding free in the same iteration.
- **Missing close() / fclose() on error paths**: file descriptors or sockets opened but not released when a subsequent operation fails, leading to fd-table exhaustion (ulimit -n).
- **Realloc without OOM guard**: `p = realloc(p, new_size);` if `realloc` fails, the original pointer is lost (memory leak *and* prior allocation becomes unreachable).
- **Unbounded string/container growth**: `strcat(dst, src)` where `dst` is a fixed-size buffer — no length check (overlap with CWE-120/787, but the resource burnout angle is the unbounded consumption of stack or heap).
- **Recursive calls without depth limit**: deeply recursive functions consuming stack frames; analysis targets recursion that depends on untrusted input size.
- **Thread / process spawning in loops**: `pthread_create()` or `fork()` called conditionally inside a loop driven by network input.

## 2. CSA Checker Architecture Recommendations

- **Base class**: `BuiltinBugChecker` (preferred) or `Checker<check::PostCall>`. For flow-sensitive tracking, `Checker<check::BranchCondition, check::DeadSymbols, check::EndFunction>`.
- **Callbacks**:
  - `check::PostCall` — intercept allocation (`malloc`, `calloc`, `realloc`), open (`open`, `fopen`, `socket`), and spawn routines (`pthread_create`, `fork`).
  - `check::DeadSymbols` / `check::EndFunction` — detect unreleased resources (leaked FD, unfreed allocation).
  - `check::LoopEnd` or `check::BranchCondition` — detect unbounded allocation inside loops (combine with loop-context analysis).
- **Tracking granularity**: track resource handles via a `ProgramStateRef` map keyed on `SymbolRef`. Count outstanding allocations per function context; emit warning when a loop-invariant allocation count exceeds a threshold (e.g., >1000 in a single loop).
- **Cross-reference**: See `docs/checker_checker_patterns.md` §3.2 (resource leak), §4.1 (loop-boundedness), and §5.3 (state explosion guards — critical for this checker because allocation-heavy paths can cause exponential states).

## 3. Known High-Frequency False Positive Patterns

- **Bounded loops misidentified as unbounded**: loops with a hidden invariant (e.g., `MAX_CHUNKS` constant, network protocol message limit) that the analyzer cannot prove is finite. Mitigation: whitelist common upper-bound idioms (`for(i=0; i<N; i++)` where `N` is a const or local capped variable).
- **Allocation in error-handling paths that never repeat**: a `malloc` in a `log_error()` path that is called at most once per request. The checker must distinguish per-request vs. per-connection vs. per-message lifetimes.
- **Static buffers / pool allocators**: custom memory pools where `malloc` is called once but the pool allocator internally reuses memory. The checker sees a single `malloc` with no `free` and flags a leak; suppression via allocator-whitelist or `known_allocator` attribute.
- **fork() in accept loop**: intentional prefork server model. The checker should suppress warnings when `fork()` is guarded by a count check (e.g., `if (children < MAX_CHILDREN) fork();`).
- **Realloc usage with temporary pointer**: the idiom `tmp = realloc(p, sz); if (!tmp) { /* handle */ } else { p = tmp; }` — the single-assignment form is safe. The checker must *not* warn on this pattern and must distinguish it from `p = realloc(p, sz)`.

## 4. Generic Discriminant Features

- **Textbook (pure CWE-400)**: allocation in a data-dependent loop with no deallocation and no cap on iterations. Easily detected — the checker can count consecutive allocations within the same basic-block loop header.
- **Variant 1 — Latent exhaustion**: allocation is bounded *per iteration* but the lifetime extends across iterations (e.g., append to a global list each time through a loop). Requires inter-procedural summary or taint tracking of the global container size.
- **Variant 2 — Side-channel exhaustion**: disk space or thread pool exhaustion via untrusted input (e.g., writing to unbounded log files). Hard to verify statically; recommend runtime monitoring or fuzz-testing integration.
- **Variant 3 — Stack exhaustion**: deep recursion whose depth is proportional to input size. The checker must identify recursive call sites where the argument is tainted and no depth guard exists (`if (depth > MAX) return;`).
- **Verdict rule**: If the resource acquisition is inside a loop whose back-edge frequency is data-dependent AND the resource is not released within the same iteration → **high confidence CWE-400**. If the loop is bounded by a const limit → **likely FP**; recommend suppression.
