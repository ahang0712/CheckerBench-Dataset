# CWE-617: Reachable Assertion
> Tier: 2 | Global samples: 57

## 1. Typical Code Patterns

An assertion (`assert()`, `_ASSERTE`, `NDEBUG-guarded check`) terminates the
process when its predicate is false.  The core flaw is placing an assertion on
**externally-influenced data** — user input, network payloads, file contents,
or any value whose shape the caller controls.  In C/C++ codebases the most
common manifestations are:

- **Parser guards on input invariants** — asserting number-of-fields, array
  indices, or buffer offsets parsed from a hostile message.
- **API contract enforcement on public entry points** — asserting that a
  pointer is non-null or a size is positive in a function that is called from
  untrusted contexts.
- **Consistency checks after allocation/decoding** — asserting that a
  `realloc()` return or a decoder status matches an expected value that an
  attacker can influence through the input.

Because `assert()` is typically compiled out in `NDEBUG` (release) builds,
these defects are often harmless in production but cause denial-of-service in
debug builds used during testing or debugging — where an attacker can use them
to force an abort.

## 2. CSA Checker Architecture Recommendations

- **Base class:** `BuiltinChecker` or `BugChecker`.
- **Callback:** `checkPreCall` / `checkPostCall` on `assert` and
  `__assert_fail` / `abort()` / `_wassert`.  A `checkEndOfTranslationUnit`
  pass can also flag unconditional `assert(false)` reachable from public
  symbols.
- **Tracking granularity:** track the symbolic expression passed to `assert()`.
  Flag any call where the predicate is derived from a **symbolic value tagged
  as externally-controlled** (e.g., argument of a function with no `static`
  linkage, data read via `fread`/`recv`).  Avoid re-warning on the same
  assertion when multiple callers reach it.
- **Cross-reference:** see `csa_checker_patterns.md` — the **taint-tracking**
  pattern applies directly; treat the assertion's condition as the sink.

## 3. Known High-Frequency False Positive Patterns

1. **Defensive assertions in debug-only harnesses.**  `assert()` inside
   `#ifndef NDEBUG` test-only code that an attacker can never invoke.  Relies
   on sound call-graph reachability analysis to prune.
2. **Internal consistency after invariant recovery.**  Assertions that fire
   only when a library-internal invariant is violated (e.g., after a sort, a
   heap property check).  These are not adversary-triggerable unless the
   invariant itself depends on external data.
3. **Assertions guarded by capability checks.**  `if (authorized) { assert(ok); }`
   — the predicate is unreachable when the guard fails.  CSA must evaluate the
   guard path-sensitively.
4. **Assertions on constant expressions.**  `assert(sizeof(T) <= MAX)` where
   the predicate is compile-time true; suppress via constant-folding.

## 4. Generic Discriminant Features

- **Textbook variant (true positive):** assertion predicate mentions a
  variable that originates from user input (`argv`, `getenv`, `read()`,
  `recv()`, parser argument) and there is no preceding sanitisation check that
  would make the predicate trivially true.
- **Variant (lower severity / false-positive-prone):** assertion inside a
  function with internal linkage (`static`) that is only called from
  `NDEBUG`-guarded test code; or the predicate is a compile-time constant, or
  the assertion is preceded by an identical explicit `if`-guard.
- **Rule of thumb:** if removing the `assert()` would expose a real
  security-sensitive side effect (e.g., buffer overflow, null deref) that is
  already checked elsewhere, the assertion is **defensive** and likely a true
  positive.  If removing it only removes an abort with no other consequence,
  the assertion is **debug-only scaffolding** and a false positive.
