# CWE-835: Loop with Unreachable Exit (Infinite Loop)
> Tier: 2 | Global samples: 41

## 1. Typical Code Patterns

The most common C/C++ infinite-loop manifestations are:

- **Missing or incorrectly placed loop-variable update** — the variable controlling loop termination is never modified inside the body (e.g., `for (int i = 0; i < n; )` without `i++`, or a `while` whose condition variable is never reassigned).
- **Condition always true due to signed/unsigned confusion** — a loop comparing a signed int to an unsigned constant produces a never-false check (e.g., `for (int i = n; i >= 0; i--)` when `n` is unsigned and wraps, or `for (unsigned i = n; i >= 0; i--)` which is always true because unsigned decrement never goes below zero).
- **Incorrect short-circuit logic in condition** — `while (x > 0 || y > 0)` where the loop body only updates one of the variables, leaving the overall condition perpetually true.
- **Pointer/integer termination that never converges** — a loop advancing through a data structure without a reachable sentinel check (e.g., walking a corrupted linked list where the next pointer never becomes NULL).
- **Exception- or branch-skipped update** — a loop where the update statement is placed after a `continue` or inside a conditional path that is skipped on every iteration.

## 2. CSA Checker Architecture Recommendations

- **Base checker class** — inherit from `BuiltinBugCheckers`; use `check::PostStmt<ForStmt>`, `check::PostStmt<WhileStmt>`, and `check::PostStmt<DoStmt>` as entry points.
- **Track reachable exit states** — for each loop, record the set of variables appearing in the condition and track their mutations across loop bodies using `ProgramStateRef` bindings. Mark the loop as "suspicious" if no state change relevant to the exit condition is observed after N symbolic iterations.
- **Bounded simulation** — re-execute the loop body up to a configurable constant bound (e.g., 20 or 40 iterations). If the exit condition remains satisfiable without any mutation of its controlling variables, report a warning.
- **Granularity** — checker-level (no per-function inline cache). Cross-reference with `csa_checker_patterns.md` §"Loop-bound checking" for path-sensitive iteration counting.

## 3. Known High-Frequency False Positive Patterns

- **Intentional busy-wait / spin-loop** — loops polling a hardware register or memory-mapped I/O where the mutation is performed by external hardware (not visible in source). Suppress if the loop contains a `volatile` access or inline assembly.
- **Loops depending on aliased or pointer-based mutation** — conditions like `while (*p != 0)` where `p` points to memory modified through another alias. The analyzer cannot always prove the aliased write happens.
- **Timeout / retry loops** — loops bounded by a counter that is decremented inside a function called in the body (out-of-line); the analyzer sees no local mutation and flags the loop.
- **Callback-driven loops** — loops whose condition is reset inside a callback invoked from within the body (e.g., event dispatch). The control-flow graph does not expose the callback's effect.
- **Loop-unswitching or compiler-generated idioms** — `do { ... } while (0)` macros or `for (;;)` patterns in header-only code that are never meant to terminate.

## 4. Generic Discriminant Features

- **Textbook (true positive):** a `for` or `while` loop whose condition references a scalar variable that is never assigned inside the body or in any reachable callee, and the body contains no `break`, `return`, `goto`, `longjmp`, or `throw` that could alter control flow.
- **Benign variant (likely FP):** the condition variable is modified but the modification is hidden behind a pointer dereference, a volatile access, an out-of-line call, or a macro expansion; the loop is a known idiom (spin-wait, event loop, listener loop).
- **Distinguishing heuristic:** if the loop body contains at least one `volatile` load/store, inline asm, `break`, or `return`, the loop is usually intentional. If none of these are present and the controlling variable is local and never written — report.
- **Repository-agnostic rule:** the fewer side effects visible to the analyzer in the loop body, the higher the confidence in a true positive. Two or more independent mutation paths (including through unknown callees) make it a likely FP.
