### Scan Script Integrity (CRITICAL)

The scan scripts (``scan/scan_before.sh``, ``scan/scan_after.sh``) are the **only
valid measurement** of N_buggy and N_patched.  They are the ground truth that the
Python-side validator will also use.  You MUST obey these rules:

**1. Never bypass the scan scripts.**  Do NOT run ``clang --analyze`` directly
   to measure warning counts.  The Python validator runs the same scan scripts
   — if you measured with a different command, your numbers will not reproduce
   and the synthesis will be rejected.

**2. If the scan script prints COMPILE_ERROR** (missing headers, undeclared
   identifiers, etc.), the scan environment needs repair.  You MUST fix it:
   - Add missing ``-I`` include paths to the flags files in ``scan/``
   - Copy needed generated headers (e.g. ``autoconf.h``) from the snapshot
   - If the file fundamentally cannot be compiled by clang, stop and write
     ``summary.json`` with ``status: "failed"`` and an honest ``failure_reason``

**3. Only trust scan script output.**  The ``Total <name> warnings: N`` line
   printed by the scan script is the number that goes into ``summary.json``.
   If the scan script says 0, write 0.  Fabricating numbers that the scan
   script did not produce will cause the Python validator to reject the
   synthesis.

- If compile fails: read the error, fix ``checker.cpp``, retry (max 3 cycles).
- If validation fails: revise checker logic, re-compile, re-scan.

## Semantic Design Contract — before writing checker.cpp

Create the analysis portions of `state.json` and `scope_statement.md` **before**
writing checker.cpp. They are a design contract, not a retrospective summary.
After compilation, update only implementation facts such as `build_attempts`.

In `patch_analysis`, distinguish the vulnerable operation, its trigger, and the
semantic fact introduced by the patch that makes it safe. In `detection_plan`,
make `report_condition`, `safe_condition`, and `source_level_signal` concrete
CSA-observable facts. In `api_choice`, record the mechanism level and explain
why the selected callback can observe and prove those facts.

In `scope_statement.md`, include this mapping table and check it again after
implementation:

| Semantic condition | CSA evidence | checker.cpp implementation |
| --- | --- | --- |
| report condition | AST / SVal / MemRegion / CFG evidence | callback, helper, and branch that reports |
| safe condition | path constraint, guard, state discharge, or structural fact | branch that suppresses the report |

Every condition in the plan must have an implementation entry. Do not claim a
condition that checker.cpp does not implement, and do not silently add a code
condition absent from the plan.

## Mechanism Selection — diagnose before coding

Choose the weakest CSA mechanism that can prove the vulnerability property:

1. **syntax-only AST**: only when local AST shape itself is the defect;
2. **control flow / dominance**: when guard placement relative to a sink matters;
3. **path-sensitive ProgramState/SVal**: when an unsafe state must reach a use;
4. **cross-procedure/dataflow**: when the required fact crosses function boundaries.

For a guard-based patch, prove both that the guard rejects the unsafe value and
that it dominates the vulnerable use. For path-sensitive or cross-procedure
defects, do not replace the required state or flow proof with local AST matching
or source-text substring matching merely because it passes the differential scan.
Record the selected level as `api_choice.mechanism_level`.

## Semantic identity, locality, and final validation

Before accepting the checker, verify that its primary matching logic does not
depend on patch-local variable names, labels, line numbers, commit IDs, or unique
literals. Project APIs, types, and stable semantic call relationships are valid
scope anchors when they define the vulnerability class. Attach the report to the
actual vulnerable operation, and implement every suppression as a real safe
condition rather than the mere presence of a nearby guard-shaped statement.

The required final sequence is: **compile → before scan → after scan → inspect
the final checker name, artifacts, and report locations → write summary.json**.
Always run the final compile and both scans. `MAX_IN_SESSION_REDESIGNS` limits only
additional redesign cycles after a failed validation; if it is zero, preserve the
real validation evidence and report failure honestly rather than fabricating counts.

## Feedback-derived requirements for this fresh synthesis

Required mechanism level: `path_sensitive`

### Current failure diagnosis

- Refinement was not accepted because the prior semantic condition remained a broad heuristic rather than a proof of an out-of-bounds firmware-buffer walk.
- Safety recognition was too dependent on specifically shaped comparisons and could miss equivalent guards with reversed operands, different relational operators, or safety established by existing operand constraints.
- A comparison could suppress a warning without proving both required bounds, proving that the rejecting branch exits, and proving that only the validated successor reaches the loop.
- The relation between the subtraction-derived bound, the pointer being walked, and the concrete firmware allocation size was not established directly enough.
- The heuristic could report unrelated or already-safe unsigned subtraction loops merely because a subtraction result controlled a constant-bounded dereferencing walk.

### Preserve from prior rollouts

- Preserve successful checker compilation, before/after validation, and code verification.
- Preserve objective eligibility gate G6.
- Preserve a path-sensitive CSA mechanism adequate for carrying facts across the subtraction, guards, intervening statements, and loop.
- Preserve semantic score at or above the configured threshold.
- Preserve process quality at or above the configured threshold.
- Remain independent of patch anchors.
- Remain free of patch-local hardcoding.

### Required semantic proof

- Establish that a runtime unsigned metadata subtraction can produce a wrapped or oversized count and that the resulting value, including through the signed destination and value-preserving casts or assignments, reaches the loop condition.
- Establish that the loop uses that count to permit dereferences through a pointer derived from the firmware data buffer and advances that pointer during iteration.
- Relate the permitted walk extent to the allocation represented by the corresponding firmware data and size, rather than accepting an arbitrary runtime value or merely a common enclosing object.
- Report only on a feasible path reaching the dangerous loop use where constraints do not prove the subtraction result is within the valid lower and allocation-size upper bounds.
- Treat a guard as protective only when its safe successor establishes the needed bound and its invalid successor cannot continue to the dangerous loop.
- Recognize semantically equivalent operand orders and relational forms when determining whether path constraints establish the required bounds.
- Do not report when existing constraints on subtraction operands or equivalent invariants already prove that the resulting walk stays within the firmware allocation.

### Implementation constraints

- Use path-sensitive CSA analysis with check::PostStmt<BinaryOperator> or equivalent evaluated-expression callbacks to identify the subtraction value and its later consumption, plus eval::Assume or an equivalent successor-specific callback to model guard branches.
- Carry value identity and validation facts in ProgramState across assignments, casts, intervening control flow, and loop entry; do not infer safety from the lexical presence of a comparison.
- Use CSA constraint queries on the current successor state to prove the normalized lower and upper bounds, including equivalent comparison orientations, instead of assigning proof flags solely from operator shape.
- Use symbolic-region relationships to connect the walked pointer to firmware data and the upper bound to the corresponding firmware allocation size.
- Require the CFG/path relationship that the validated successor reaches the loop while the rejecting successor exits or otherwise cannot reach the dangerous use.
- Keep analysis intra-function because the supplied defect and fix require no interprocedural propagation.
- Anchor the diagnostic at the dangerous loop condition or associated buffer dereference and mark the subtraction-derived symbol as interesting.
- Generalize over declarations, symbols, regions, and control flow without file names, function names, variable names, source lines, commit identifiers, or patch literals.

### Validation checklist

- Compile the new checker as a loadable CSA plugin with the target LLVM/Clang API and verify checker registration and analyzer loading.
- Scan both supplied buggy inputs and require the established two relevant diagnostics in sof_ipc3_fw_parse_ext_man with no diagnostics in non-patched functions.
- Scan both supplied patched inputs and require zero diagnostics, with both buggy diagnostics disappearing only because the new bounds-and-exit control flow proves safety.
- Run code verification and retain diagnostics within the patched function and near the dangerous subtraction-to-loop sequence, with no unrelated disappeared warnings.
- Add refinement cases for reversed operands and equivalent strict or non-strict lower- and upper-bound comparisons; all genuinely safe continuations must suppress.
- Add cases where a comparison is unrelated, bounds the wrong value or allocation, or has a rejecting branch that still reaches the loop; these must not suppress.
- Add safe cases where operand constraints independently prevent underflow or prove the walk extent is within the allocation; these must remain clean.
- Add unsafe and unrelated-loop cases to confirm that semantically equivalent unchecked firmware walks report while generic unsigned subtraction loops do not.

### Avoid and forbidden regressions

- Do not reduce the mechanism to syntax-only or control-flow-only matching; successor-specific symbolic facts are required.
- Do not treat every relational comparison involving the subtraction as validation.
- Do not recognize only a suspect-on-the-left form or only the exact operators shown in the patch.
- Do not grant a bound proof to both branch successors or to a continuation whose rejecting path can still reach the loop.
- Do not equate shared region ancestry alone with proof that the bound is the size of the allocation actually being walked.
- Do not report every runtime unsigned subtraction used as a constant loop bound without proving the firmware-buffer dereference and advance relationship.
- Do not rely on source text, patch locations, project identifiers, declaration spellings, or exact patch expressions.
- Do not suppress warnings merely to reproduce the observed before/after counts when the required safety relation is unproven.
