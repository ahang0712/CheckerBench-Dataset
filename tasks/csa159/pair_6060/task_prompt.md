### Scan Script Integrity (CRITICAL)

The scan scripts (``scan/scan_before.sh``, ``scan/scan_after.sh``) are the **only
valid measurement** of N_buggy and N_patched.  They are the ground truth that the
Python-side validator will also use.  You MUST obey these rules:

**1. Never bypass the scan scripts.**  Do NOT run ``clang --analyze`` directly
   to measure warning counts.  The Python validator runs the same scan scripts
   — if you measured with a different command, your numbers will not reproduce
   and the synthesis will be rejected.

**2. If the scan script prints COMPILE_ERROR** (missing headers, undeclared
   identifiers, etc.), the scan environment needs repair.  You MUST fix it:
   - Add missing ``-I`` include paths to the flags files in ``scan/``
   - Copy needed generated headers (e.g. ``autoconf.h``) from the snapshot
   - If the file fundamentally cannot be compiled by clang, stop and write
     ``summary.json`` with ``status: "failed"`` and an honest ``failure_reason``

**3. Only trust scan script output.**  The ``Total <name> warnings: N`` line
   printed by the scan script is the number that goes into ``summary.json``.
   If the scan script says 0, write 0.  Fabricating numbers that the scan
   script did not produce will cause the Python validator to reject the
   synthesis.

- If compile fails: read the error, fix ``checker.cpp``, retry (max 3 cycles).
- If validation fails: revise checker logic, re-compile, re-scan.

## Semantic Design Contract — before writing checker.cpp

Create the analysis portions of `state.json` and `scope_statement.md` **before**
writing checker.cpp. They are a design contract, not a retrospective summary.
After compilation, update only implementation facts such as `build_attempts`.

In `patch_analysis`, distinguish the vulnerable operation, its trigger, and the
semantic fact introduced by the patch that makes it safe. In `detection_plan`,
make `report_condition`, `safe_condition`, and `source_level_signal` concrete
CSA-observable facts. In `api_choice`, record the mechanism level and explain
why the selected callback can observe and prove those facts.

In `scope_statement.md`, include this mapping table and check it again after
implementation:

| Semantic condition | CSA evidence | checker.cpp implementation |
| --- | --- | --- |
| report condition | AST / SVal / MemRegion / CFG evidence | callback, helper, and branch that reports |
| safe condition | path constraint, guard, state discharge, or structural fact | branch that suppresses the report |

Every condition in the plan must have an implementation entry. Do not claim a
condition that checker.cpp does not implement, and do not silently add a code
condition absent from the plan.

## Mechanism Selection — diagnose before coding

Choose the weakest CSA mechanism that can prove the vulnerability property:

1. **syntax-only AST**: only when local AST shape itself is the defect;
2. **control flow / dominance**: when guard placement relative to a sink matters;
3. **path-sensitive ProgramState/SVal**: when an unsafe state must reach a use;
4. **cross-procedure/dataflow**: when the required fact crosses function boundaries.

For a guard-based patch, prove both that the guard rejects the unsafe value and
that it dominates the vulnerable use. For path-sensitive or cross-procedure
defects, do not replace the required state or flow proof with local AST matching
or source-text substring matching merely because it passes the differential scan.
Record the selected level as `api_choice.mechanism_level`.

## Semantic identity, locality, and final validation

Before accepting the checker, verify that its primary matching logic does not
depend on patch-local variable names, labels, line numbers, commit IDs, or unique
literals. Project APIs, types, and stable semantic call relationships are valid
scope anchors when they define the vulnerability class. Attach the report to the
actual vulnerable operation, and implement every suppression as a real safe
condition rather than the mere presence of a nearby guard-shaped statement.

The required final sequence is: **compile → before scan → after scan → inspect
the final checker name, artifacts, and report locations → write summary.json**.
Always run the final compile and both scans. `MAX_IN_SESSION_REDESIGNS` limits only
additional redesign cycles after a failed validation; if it is zero, preserve the
real validation evidence and report failure honestly rather than fabricating counts.

## Feedback-derived requirements for this fresh synthesis

A prior independent rollout exposed the risks below. Start again from the patch
in this new session. Do not reconstruct, edit, or assume the prior checker.

Required mechanism level: `control_flow`

### Current failure diagnosis

- The rollout failed the process-quality threshold despite compiling, passing paired validation, and producing five relevant pre-patch diagnostics with none post-patch.
- The syntax-only interval design over-approximated the defect because it ignored reachability and dominating bounds checks; notably, BMF_BPP[iBitmapFormat] is reached only after iBitmapFormat values at or above the table extent branch to fail.
- Function-wide assignment collection ignored statement order and controlling branches, so it could associate definitions that do not reach a subscript.
- The claimed tightness of interval endpoints was unsound for correlated expressions such as x-x and for some transformed masked values.
- The analysis incorrectly characterized lookup operations in write-side functions as out-of-bounds writes; these are out-of-bounds reads from lookup tables used while serializing output.
- The plan underrepresented the patch's rejection of unsupported but array-in-bounds encodings, which is distinct from memory bounds safety.

### Preserve from prior rollouts

- The synthesized checker must compile successfully and retain successful before/after validation and code verification.
- Retain objective eligibility gate G6.
- Retain an accepted or clean refinement outcome.
- Use a CSA mechanism at least as strong as the previously accepted syntax-only mechanism.
- Maintain the semantic score at or above the configured threshold.
- Raise and maintain process quality at or above the configured threshold.
- Remain independent of patch anchors such as changed line numbers, commit identifiers, function names, accessor names, and deleted table names.
- Remain free of patch-local hardcoding and project-specific scope.

### Required semantic proof

- At each qualifying ArraySubscriptExpr, establish that the base denotes a fixed-extent constant integer array with extent N.
- Establish from sound integer-domain evidence that an index value below zero or at least N can reach the subscript along a feasible CFG path.
- Treat a bounds check as protective only when its in-bounds successor dominates or otherwise necessarily controls the subscript and the rejecting successor cannot reach it.
- Suppress BMF_BPP[iBitmapFormat] when the preceding iBitmapFormat >= ARRAYSIZE(BMF_BPP) check transfers all out-of-range values to fail before the access.
- Report the unguarded CBR2_BPP, CBR23_BPP, BPP_CBR2, BPP_CBR23, and BPP_BMF accesses where their reachable index domains exceed their extents.
- Distinguish memory-safety proof from accepted-encoding validation: unsupported values that remain within the old array extent are not OOB solely because the patch later rejects them.

### Implementation constraints

- Use a CSA callback and local CFG analysis capable of relating an ArraySubscriptExpr to preceding guards, assignments, branches, and terminating or fail edges; control-flow reasoning is required, but ProgramState tracking and interprocedural propagation are not.
- Compute reaching definitions or equivalent ordered local facts rather than collecting every assignment in the function without regard to CFG position.
- Use sound AST and type semantics for constants, casts, masks, shifts, and integer ranges; do not claim endpoint attainability when operands are correlated unless that claim is proven.
- Recognize protective comparisons in semantically equivalent operand orders and branch forms, and require the protective relation to hold on every path reaching the sink.
- Report at the unsafe array subscript and include its source range; do not report at a declaration, guard, parser call, or replacement accessor.
- Keep scope project-general through array extent, const qualification, integer element type, index semantics, and CFG relations rather than FreeRDP identifiers.
- Limit the checker to lookup-table OOB reads; do not label accesses in serialization functions as writes to the lookup table.
- Do not infer protocol-valid value sets from initializer contents such as zero entries unless a separate, evidence-backed semantic rule proves that contract.

### Validation checklist

- Build and load the checker against the required Clang Static Analyzer API without compilation, registration, or analyzer failures.
- Scan the vulnerable source and confirm diagnostics at the five unguarded unsafe lookup subscripts identified by paired verification.
- Confirm no diagnostic for the guarded BMF_BPP[iBitmapFormat] access because its rejecting check prevents out-of-range values from reaching the subscript.
- Scan the patched source and confirm zero diagnostics after raw lookup subscripts are replaced by validating accessors.
- Verify every vulnerable diagnostic is located on the corresponding ArraySubscriptExpr with median distance zero from the relevant patch site and no reports in non-patched functions.
- Add refinement cases for a dominating upper-bound guard, a non-dominating guard, reversed comparison operands, early return or goto rejection, and assignment after validation.
- Add arithmetic refinement cases covering correlated expressions such as x-x, masked and shifted indices, narrowing casts, signed negative ranges, and multiple reaching definitions.

### Avoid and forbidden regressions

- Do not reuse the syntax-only shortcut that reports from a declared or assignment-derived range without checking whether out-of-bounds values can reach the access.
- Do not suppress merely because a nearby statement resembles a guard; prove its CFG relationship and rejecting behavior.
- Do not perform function-wide unordered assignment aggregation.
- Do not propagate interval tightness mechanically through operations involving correlated operands.
- Do not report the guarded BMF_BPP access as vulnerable.
- Do not conflate unsupported in-bounds encodings with out-of-bounds memory access.
- Do not introduce names, line locations, table extents, mask constants, or patch-specific accessor patterns as matching anchors.
- Do not add ProgramState or interprocedural dataflow unless CFG-local proof is shown insufficient by new evidence.
