### Scan Script Integrity (CRITICAL)

The scan scripts (``scan/scan_before.sh``, ``scan/scan_after.sh``) are the **only
valid measurement** of N_buggy and N_patched.  They are the ground truth that the
Python-side validator will also use.  You MUST obey these rules:

**1. Never bypass the scan scripts.**  Do NOT run ``clang --analyze`` directly
   to measure warning counts.  The Python validator runs the same scan scripts
   — if you measured with a different command, your numbers will not reproduce
   and the synthesis will be rejected.

**2. If the scan script prints COMPILE_ERROR** (missing headers, undeclared
   identifiers, etc.), the scan environment needs repair.  You MUST fix it:
   - Add missing ``-I`` include paths to the flags files in ``scan/``
   - Copy needed generated headers (e.g. ``autoconf.h``) from the snapshot
   - If the file fundamentally cannot be compiled by clang, stop and write
     ``summary.json`` with ``status: "failed"`` and an honest ``failure_reason``

**3. Only trust scan script output.**  The ``Total <name> warnings: N`` line
   printed by the scan script is the number that goes into ``summary.json``.
   If the scan script says 0, write 0.  Fabricating numbers that the scan
   script did not produce will cause the Python validator to reject the
   synthesis.

- If compile fails: read the error, fix ``checker.cpp``, retry (max 3 cycles).
- If validation fails: revise checker logic, re-compile, re-scan.

## Semantic Design Contract — before writing checker.cpp

Create the analysis portions of `state.json` and `scope_statement.md` **before**
writing checker.cpp. They are a design contract, not a retrospective summary.
After compilation, update only implementation facts such as `build_attempts`.

In `patch_analysis`, distinguish the vulnerable operation, its trigger, and the
semantic fact introduced by the patch that makes it safe. In `detection_plan`,
make `report_condition`, `safe_condition`, and `source_level_signal` concrete
CSA-observable facts. In `api_choice`, record the mechanism level and explain
why the selected callback can observe and prove those facts.

In `scope_statement.md`, include this mapping table and check it again after
implementation:

| Semantic condition | CSA evidence | checker.cpp implementation |
| --- | --- | --- |
| report condition | AST / SVal / MemRegion / CFG evidence | callback, helper, and branch that reports |
| safe condition | path constraint, guard, state discharge, or structural fact | branch that suppresses the report |

Every condition in the plan must have an implementation entry. Do not claim a
condition that checker.cpp does not implement, and do not silently add a code
condition absent from the plan.

## Mechanism Selection — diagnose before coding

Choose the weakest CSA mechanism that can prove the vulnerability property:

1. **syntax-only AST**: only when local AST shape itself is the defect;
2. **control flow / dominance**: when guard placement relative to a sink matters;
3. **path-sensitive ProgramState/SVal**: when an unsafe state must reach a use;
4. **cross-procedure/dataflow**: when the required fact crosses function boundaries.

For a guard-based patch, prove both that the guard rejects the unsafe value and
that it dominates the vulnerable use. For path-sensitive or cross-procedure
defects, do not replace the required state or flow proof with local AST matching
or source-text substring matching merely because it passes the differential scan.
Record the selected level as `api_choice.mechanism_level`.

## Semantic identity, locality, and final validation

Before accepting the checker, verify that its primary matching logic does not
depend on patch-local variable names, labels, line numbers, commit IDs, or unique
literals. Project APIs, types, and stable semantic call relationships are valid
scope anchors when they define the vulnerability class. Attach the report to the
actual vulnerable operation, and implement every suppression as a real safe
condition rather than the mere presence of a nearby guard-shaped statement.

The required final sequence is: **compile → before scan → after scan → inspect
the final checker name, artifacts, and report locations → write summary.json**.
Always run the final compile and both scans. `MAX_IN_SESSION_REDESIGNS` limits only
additional redesign cycles after a failed validation; if it is zero, preserve the
real validation evidence and report failure honestly rather than fabricating counts.

## Feedback-derived requirements for this fresh synthesis

A prior independent rollout exposed the risks below. Start again from the patch
in this new session. Do not reconstruct, edit, or assume the prior checker.

Required mechanism level: `control_flow`

### Current failure diagnosis

- Refinement was not accepted because the prior semantic model classified safety by record type and function membership rather than proving the lifetime state of the particular object reaching the free.
- Type-wide RCU classification can report immediate frees of unpublished objects or objects already protected by a completed grace period.
- Function-wide deferred-callback closure can suppress a helper whenever it is reachable from an RCU callback, even if the same helper is also called directly from a non-callback context.
- The analysis omitted the patch's publication reordering: the patched error path immediately frees only before rcu_assign_pointer publishes the object, while the successful published path defers destruction.
- RCU macro traversal could collect every pointer-to-record expression in the macro subtree instead of identifying only the accessor's published object type.
- Process quality remained below threshold because patch understanding and the detection plan did not fully cover publication ordering and calling-context distinctions, despite successful compilation and differential scans.

### Preserve from prior rollouts

- Preserve successful checker compilation, before/after validation, and code verification.
- Preserve objective eligibility gate G6.
- Preserve a CSA mechanism at least as strong as the previously accepted cross-procedure control-flow analysis.
- Preserve the semantic score at or above the configured threshold.
- Remain independent of patch anchors such as changed line numbers or diff-specific locations.
- Remain free of patch-local hardcoding, including the affected function, field, and record names.

### Required semantic proof

- Prove that the specific object reaching an immediate release is reachable from an RCU publication on the relevant control-flow and call path, rather than inferring publication from its record type alone.
- Prove that an immediate release after publication can occur without an intervening RCU grace-period mechanism, allowing a pre-existing rcu_dereference reader to retain and access stale storage.
- Treat an immediate release on an error path as safe when that path reaches the release before the object is published; this distinction is required by the patched smb_grant_oplock ordering.
- Treat a release reached through a call_rcu-family callback as deferred only for callback-rooted call contexts.
- Do not suppress a shared release helper merely because one caller is an RCU callback; preserve diagnostics for independently reachable non-callback contexts.
- Recognize the original defect as publication followed by last-reference immediate destruction, while recognizing the patch as separating unpublished cleanup from post-publication deferred destruction.

### Implementation constraints

- Use check::PreCall, or an equivalently precise CSA call callback, to inspect immediate release operations and anchor each diagnostic at the actual releasing call and its freed argument.
- Build translation-unit control-flow and direct-call relationships needed to connect RCU publication sites, release paths, and call_rcu-family callback registrations across functions.
- Associate publication and release evidence through the relevant expression, declaration, field, parameter, or call-edge identity; a canonical RecordDecl match alone is insufficient.
- Determine deferred safety from callback-rooted calling paths, accounting for helpers that also have non-callback callers instead of assigning unconditional safety to the helper FunctionDecl.
- Use AST macro-expansion and canonical type evidence to identify the actual pointer operand of RCU accessor or publication operations without indiscriminately collecting unrelated pointer types from the macro subtree.
- Do not require path-sensitive ProgramState modeling of concurrent readers or reference counts; the required proof is static ordering and reachability across the translation unit.
- Keep scope project-general by relying only on stable kernel RCU, allocator, and deferred-release APIs plus structural AST and call-graph relations.
- Register a normal CSA checker and emit nonfatal reports without source-text matching, changed-line tests, or identifiers unique to this patch.

### Validation checklist

- Compile the new checker as a loadable CSA plugin with the target LLVM/Clang API and complete code verification without diagnostics.
- Scan both supplied before and after source states using equivalent compilation flags; require diagnostics in the buggy state and no diagnostics in the patched state.
- Confirm buggy diagnostics are attached to the immediate kfree operation for the published oplock object and remain within the relevant patched function scope.
- Confirm the patched call_rcu callback path to the raw release helper is considered deferred and produces no report.
- Confirm the patched err_out path through the raw immediate-release helper produces no report because publication has not yet occurred on that path.
- Add a refinement case where one release helper is called from both an RCU callback and a normal caller; require suppression only for the callback-rooted path.
- Add a refinement case with an immediate free of the same record type but no publication of that object; require no report.
- Verify that RCU macro analysis selects the published pointer operand and does not classify unrelated pointer-to-record expressions nested in the expansion.

### Avoid and forbidden regressions

- Do not reuse the type-wide rule that every immediate free of an RCU-observed record type is vulnerable.
- Do not use a function-wide deferred-free set that erases distinctions between callback and direct calling contexts.
- Do not ignore the movement of rcu_assign_pointer after failure-prone initialization or treat the patched immediate error cleanup as unsafe.
- Do not approximate the publication operand by collecting all pointer expressions encountered inside an RCU macro expansion.
- Do not replace the required ordering and cross-procedure reachability proof with a syntax-only call or declaration match.
- Do not attempt to model cross-thread RCU readers through a single exploded path or claim sound concrete concurrency modeling from ProgramState.
- Do not key behavior to free_opinfo, __free_opinfo, free_opinfo_rcu, oplock_info, f_opinfo, ksmbd paths, patch line numbers, or unique patch literals.
