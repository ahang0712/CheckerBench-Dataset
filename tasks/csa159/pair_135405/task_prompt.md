### Scan Script Integrity (CRITICAL)

The scan scripts (``scan/scan_before.sh``, ``scan/scan_after.sh``) are the **only
valid measurement** of N_buggy and N_patched.  They are the ground truth that the
Python-side validator will also use.  You MUST obey these rules:

**1. Never bypass the scan scripts.**  Do NOT run ``clang --analyze`` directly
   to measure warning counts.  The Python validator runs the same scan scripts
   — if you measured with a different command, your numbers will not reproduce
   and the synthesis will be rejected.

**2. If the scan script prints COMPILE_ERROR** (missing headers, undeclared
   identifiers, etc.), the scan environment needs repair.  You MUST fix it:
   - Add missing ``-I`` include paths to the flags files in ``scan/``
   - Copy needed generated headers (e.g. ``autoconf.h``) from the snapshot
   - If the file fundamentally cannot be compiled by clang, stop and write
     ``summary.json`` with ``status: "failed"`` and an honest ``failure_reason``

**3. Only trust scan script output.**  The ``Total <name> warnings: N`` line
   printed by the scan script is the number that goes into ``summary.json``.
   If the scan script says 0, write 0.  Fabricating numbers that the scan
   script did not produce will cause the Python validator to reject the
   synthesis.

- If compile fails: read the error, fix ``checker.cpp``, retry (max 3 cycles).
- If validation fails: revise checker logic, re-compile, re-scan.

## Semantic Design Contract — before writing checker.cpp

Create the analysis portions of `state.json` and `scope_statement.md` **before**
writing checker.cpp. They are a design contract, not a retrospective summary.
After compilation, update only implementation facts such as `build_attempts`.

In `patch_analysis`, distinguish the vulnerable operation, its trigger, and the
semantic fact introduced by the patch that makes it safe. In `detection_plan`,
make `report_condition`, `safe_condition`, and `source_level_signal` concrete
CSA-observable facts. In `api_choice`, record the mechanism level and explain
why the selected callback can observe and prove those facts.

In `scope_statement.md`, include this mapping table and check it again after
implementation:

| Semantic condition | CSA evidence | checker.cpp implementation |
| --- | --- | --- |
| report condition | AST / SVal / MemRegion / CFG evidence | callback, helper, and branch that reports |
| safe condition | path constraint, guard, state discharge, or structural fact | branch that suppresses the report |

Every condition in the plan must have an implementation entry. Do not claim a
condition that checker.cpp does not implement, and do not silently add a code
condition absent from the plan.

## Mechanism Selection — diagnose before coding

Choose the weakest CSA mechanism that can prove the vulnerability property:

1. **syntax-only AST**: only when local AST shape itself is the defect;
2. **control flow / dominance**: when guard placement relative to a sink matters;
3. **path-sensitive ProgramState/SVal**: when an unsafe state must reach a use;
4. **cross-procedure/dataflow**: when the required fact crosses function boundaries.

For a guard-based patch, prove both that the guard rejects the unsafe value and
that it dominates the vulnerable use. For path-sensitive or cross-procedure
defects, do not replace the required state or flow proof with local AST matching
or source-text substring matching merely because it passes the differential scan.
Record the selected level as `api_choice.mechanism_level`.

## Semantic identity, locality, and final validation

Before accepting the checker, verify that its primary matching logic does not
depend on patch-local variable names, labels, line numbers, commit IDs, or unique
literals. Project APIs, types, and stable semantic call relationships are valid
scope anchors when they define the vulnerability class. Attach the report to the
actual vulnerable operation, and implement every suppression as a real safe
condition rather than the mere presence of a nearby guard-shaped statement.

The required final sequence is: **compile → before scan → after scan → inspect
the final checker name, artifacts, and report locations → write summary.json**.
Always run the final compile and both scans. `MAX_IN_SESSION_REDESIGNS` limits only
additional redesign cycles after a failed validation; if it is zero, preserve the
real validation evidence and report failure honestly rather than fabricating counts.

## Feedback-derived requirements for this fresh synthesis

A prior independent rollout exposed the risks below. Start again from the patch
in this new session. Do not reconstruct, edit, or assume the prior checker.

Required mechanism level: `control_flow`

### Current failure diagnosis

- The prior rollout did not prove that a candidate condition constrains the accumulated output length; it accepted any relational comparison with an operand at least as large as the capacity.
- Source-order precedence was substituted for reachability and dominance, so a guard on another branch or a bypassable guard could incorrectly suppress a real overflow.
- Termination was recognized without proving comparison orientation or which successor reaches the writes; accepting arbitrary return, goto, break, or continue constructs made the safe condition unsound.
- Treating every nonliteral source as unbounded ignored the cumulative semantics of repeated concatenation, including argument lengths, separators, newline, and the terminating null byte.
- Process quality remained below threshold because validation included working-directory mistakes, an avoidable CSA API type error, unreliable scans with compile errors, and some weakly evidenced recovery steps.

### Preserve from prior rollouts

- The new synthesis must compile successfully and pass before/after validation and code verification.
- Preserve objective eligibility gate G6.
- Preserve an accepted or clean refinement outcome.
- Maintain the semantic score at or above the configured threshold while correcting the semantic mechanism.
- Remain independent of patch anchors such as changed line numbers or exact diff locations.
- Remain free of patch-local hardcoding, including project-specific function, variable, file, or macro names.

### Required semantic proof

- Report only when repeated unbounded string writes can reach a fixed-capacity destination without a proven bound on the total required bytes.
- Relate the checked quantity to the same accumulated length consumed by the writes, accounting for each source length, inserted separators, the final newline, and null termination.
- A suppressing guard must compare that accumulated requirement against the destination capacity with the correct operator and operand orientation.
- Prove through the CFG that the rejecting successor exits before every relevant write and that every path reaching those writes passed through the safe successor.
- For the patched structure, establish that completion of the length-accumulation loop and the condition len >= capacity imply len < capacity on all paths entering the later concatenation loop.
- Do not infer safety merely from a nonliteral source being preceded by some capacity-like comparison; absence or presence of the precise length-to-capacity relation controls the diagnostic.

### Implementation constraints

- Use check::PreCall, or an equivalently local pre-write callback, for strcat/strcpy so destination and source arguments are available and the diagnostic is emitted at the unsafe call.
- Recover the destination extent from CSA region and type information, including an inlined caller's fixed array when observable, rather than from spelling or a literal capacity value.
- Use the enclosing AnalysisDeclContext CFG and dominance or equivalent all-path reachability reasoning; SourceManager ordering alone is insufficient.
- Identify the length accumulator by its data dependencies on strlen-derived source lengths and added delimiter costs, not by its identifier.
- Accept a guard only when its safe CFG edge dominates the relevant writes and its rejecting edge cannot rejoin before them.
- Resolve a size parameter to a concrete destination capacity only through semantic argument/type relationships such as sizeof of the same destination; do not guess from parameter position or value alone.
- Keep scope project-general around fixed-capacity destinations and standard unbounded string-copy or concatenation sinks, with no special treatment of ext-cmd.c, cmd_client, append_strings, buffer, len, bufsize, argv, or 256.
- Avoid persistent ProgramState traits or cross-function fact propagation unless CFG and call-context facts demonstrably cannot establish the required relation.

### Validation checklist

- Build the new checker against the supplied LLVM/Clang API with no diagnostics and verify registration and loading before scanning.
- Run scans from verified working directories with the supplied include flags; reject any result in which either source version has a compile error or skipped file.
- Confirm exactly the relevant vulnerable-version diagnostic is produced and the patched version is clean, preserving N_buggy=1 and N_patched=0.
- Confirm the vulnerable diagnostic is located on the length-unknown strcat in cmd_client, at zero or comparably minimal distance from the changed vulnerable operation.
- Add focused negative tests showing that an unrelated large-constant comparison, reversed or permissive comparison, terminating wrong branch, source-ordered but bypassable guard, or nondominating guard does not establish safety.
- Add a positive safety test matching the patch semantics: accumulated strlen plus delimiter costs is rejected at or above the same buffer capacity before all concatenations.
- Run code verification and ensure no warnings disappear only in non-patched functions and no unrelated strcpy to a struct field is newly diagnosed outside the declared scope.
- Complete refinement with an accepted or clean outcome and retain objective gate G6 and the configured semantic-score threshold.

### Avoid and forbidden regressions

- Do not reuse the failed heuristic of collecting arbitrary preceding IfStmt nodes and accepting any capacity-sized operand plus any syntactically nested terminator.
- Do not equate lexical source order with dominance, path reachability, or enforcement of a guard.
- Do not suppress on a comparison unless the checker proves accumulator identity, comparison direction, rejecting successor, and the path relationship to every sink.
- Do not use a pure strcat/strcpy syntax match or fixed-array plus nonliteral-source match; those patterns cannot distinguish the patched helper from the vulnerability.
- Do not introduce unnecessary caller-to-callee dataflow or symbolic-state machinery merely to recover a literal value when semantic CFG and argument relationships suffice.
- Do not rely on file paths, source lines, patch anchors, project identifiers, exact variable names, or the literal capacity 256.
- Do not count scans with parse failures, missing headers, invalid flags, or unverified recovery commands as validation evidence.
