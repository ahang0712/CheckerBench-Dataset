### Scan Script Integrity (CRITICAL)

The scan scripts (``scan/scan_before.sh``, ``scan/scan_after.sh``) are the **only
valid measurement** of N_buggy and N_patched.  They are the ground truth that the
Python-side validator will also use.  You MUST obey these rules:

**1. Never bypass the scan scripts.**  Do NOT run ``clang --analyze`` directly
   to measure warning counts.  The Python validator runs the same scan scripts
   — if you measured with a different command, your numbers will not reproduce
   and the synthesis will be rejected.

**2. If the scan script prints COMPILE_ERROR** (missing headers, undeclared
   identifiers, etc.), the scan environment needs repair.  You MUST fix it:
   - Add missing ``-I`` include paths to the flags files in ``scan/``
   - Copy needed generated headers (e.g. ``autoconf.h``) from the snapshot
   - If the file fundamentally cannot be compiled by clang, stop and write
     ``summary.json`` with ``status: "failed"`` and an honest ``failure_reason``

**3. Only trust scan script output.**  The ``Total <name> warnings: N`` line
   printed by the scan script is the number that goes into ``summary.json``.
   If the scan script says 0, write 0.  Fabricating numbers that the scan
   script did not produce will cause the Python validator to reject the
   synthesis.

- If compile fails: read the error, fix ``checker.cpp``, retry (max 3 cycles).
- If validation fails: revise checker logic, re-compile, re-scan.

## Semantic Design Contract — before writing checker.cpp

Create the analysis portions of `state.json` and `scope_statement.md` **before**
writing checker.cpp. They are a design contract, not a retrospective summary.
After compilation, update only implementation facts such as `build_attempts`.

In `patch_analysis`, distinguish the vulnerable operation, its trigger, and the
semantic fact introduced by the patch that makes it safe. In `detection_plan`,
make `report_condition`, `safe_condition`, and `source_level_signal` concrete
CSA-observable facts. In `api_choice`, record the mechanism level and explain
why the selected callback can observe and prove those facts.

In `scope_statement.md`, include this mapping table and check it again after
implementation:

| Semantic condition | CSA evidence | checker.cpp implementation |
| --- | --- | --- |
| report condition | AST / SVal / MemRegion / CFG evidence | callback, helper, and branch that reports |
| safe condition | path constraint, guard, state discharge, or structural fact | branch that suppresses the report |

Every condition in the plan must have an implementation entry. Do not claim a
condition that checker.cpp does not implement, and do not silently add a code
condition absent from the plan.

## Mechanism Selection — diagnose before coding

Choose the weakest CSA mechanism that can prove the vulnerability property:

1. **syntax-only AST**: only when local AST shape itself is the defect;
2. **control flow / dominance**: when guard placement relative to a sink matters;
3. **path-sensitive ProgramState/SVal**: when an unsafe state must reach a use;
4. **cross-procedure/dataflow**: when the required fact crosses function boundaries.

For a guard-based patch, prove both that the guard rejects the unsafe value and
that it dominates the vulnerable use. For path-sensitive or cross-procedure
defects, do not replace the required state or flow proof with local AST matching
or source-text substring matching merely because it passes the differential scan.
Record the selected level as `api_choice.mechanism_level`.

## Semantic identity, locality, and final validation

Before accepting the checker, verify that its primary matching logic does not
depend on patch-local variable names, labels, line numbers, commit IDs, or unique
literals. Project APIs, types, and stable semantic call relationships are valid
scope anchors when they define the vulnerability class. Attach the report to the
actual vulnerable operation, and implement every suppression as a real safe
condition rather than the mere presence of a nearby guard-shaped statement.

The required final sequence is: **compile → before scan → after scan → inspect
the final checker name, artifacts, and report locations → write summary.json**.
Always run the final compile and both scans. `MAX_IN_SESSION_REDESIGNS` limits only
additional redesign cycles after a failed validation; if it is zero, preserve the
real validation evidence and report failure honestly rather than fabricating counts.

### Preserve from prior rollouts

- Do not introduce dependence on the changed line, patch hunk, or another patch anchor.
- Do not introduce hardcoding for macsmc.c, apple_smc_probe, apple_smc_read, apple_smc_read_u32, smc, or the CVE.

### Required semantic proof

- Prove on one analyzed path that an object came from a relevant kernel heap allocator and that the acquired region is a struct mutex field of that same object.
- Prove that no mutex_init or __mutex_init of the same mutex region occurs after allocation and before the acquisition on that path.
- Carry allocation and initialization facts through the helper frames and inlined guard expansion that separate apple_smc_probe from the mutex acquisition.
- Treat a preceding initialization of the same field as safe while retaining warnings for sibling mutex fields that were not initialized.
- Do not infer uninitialized provenance for a mutex reached only through an unconstrained external parameter.

### Implementation constraints

- Use path-sensitive ProgramState propagated across inlined calls; observe allocator and initialization effects with call callbacks and inspect mutex acquisition before the call executes.
- Canonicalize symbolic allocation results, casts, derived regions, and FieldRegions so allocation, mutex_init, and mutex_lock arguments can be compared by stable object and field identity.
- Recognize struct mutex by semantic type information and model stable Linux allocator, mutex initialization, and mutex acquisition API families rather than source text.
- Model the guard(mutex) expansion through the acquisition CallEvent it produces; do not require a directly written mutex_lock expression.
- Keep initialization facts path-specific so an init on one branch does not suppress an unsafe branch, and account for reallocation or symbol lifetime when retaining tracked facts.
- Emit the primary diagnostic at the allocation or earliest source-level call in the patched function that reaches the unsafe acquisition, with path notes identifying allocation and acquisition when available.
- Limit scope to allocated objects containing struct mutex fields; do not generalize the result to spinlocks, completions, rwsems, or unrelated zero-initialized fields.

### Validation checklist

- Build the new checker as a loadable CSA plugin with the target Clang version and confirm registration under its configured checker name.
- Run the authoritative before scan and require at least one warning on the buggy revision; zero warnings is a hard failure regardless of any separate summary.
- Run the identical scan on the patched revision and require the relevant warning to disappear, with N_buggy greater than N_patched and N_patched below the harness threshold.
- Confirm the disappearing diagnostic is attributed within drivers/mfd/macsmc.c::apple_smc_probe or the verifier's precise changed-span policy, while its path explains the downstream mutex acquisition.
- Add a refinement where mutex_init of the same field dominates acquisition and verify suppression, plus a branch refinement where only one path initializes and verify the unsafe path remains reportable.
- Check alias and cast refinements between allocation, initialization, and lock arguments, including the inlined guard helper chain.
- Verify standalone analysis of helper entry points with unknown object provenance does not report, and verify initialization of one mutex field does not suppress a sibling field.
- Produce non-missing hard-validation, refinement, semantic, objective, and process results from the same built artifact and reconcile all warning counts.

### Avoid and forbidden regressions

- Do not use textual proximity, local AST matching, or declaration presence as a substitute for proving path ordering and object identity.
- Do not use translation-unit-wide presence of mutex_init to suppress acquisitions; an initialization must precede the same-field acquisition on the same path.
- Do not repeat the unverified assumption that PostCall allocator return regions automatically equal the later field base region.
- Do not treat zero-filled allocation as valid mutex initialization.
- Do not report every lock of an allocated object without confirming that the lock argument is an embedded struct mutex field.
- Do not rely on stale claimed scan counts when authoritative verification reports zero detections.
- Do not attribute the primary report only to an inlined header or macro implementation site that the relevance gate cannot associate with the patched function.
